# 工作搭子工具箱 · 开发指南

> 一份给你（以及你自己的 CalDAV 日历工具）借鉴用的架构说明。
> 核心思想：**用一份纯文本 Markdown 当「唯一事实源」，所有前端 / AI Agent / 定时任务都围绕它读写。**
> 本指南不绑定任何具体平台，你拿去改造成自己的工具完全没问题。

---

## 0. 先给结论：这个思路怎么样？

**非常好，而且是被反复验证过的成熟模式。** 你描述的「写到本地 md → 第三方 AI 处理这些 md → 日历/任务工具定时解析或手动同步 md 来创建任务」本质就是 **Plain-Text-as-Source-of-Truth（纯文本作为数据层）** 模式。

为什么它成立、为什么适合你：

| 维度 | 说明 |
|------|------|
| **LLM 原生** | 任何 AI Agent（Claude Code / Cursor / 你自己的脚本 / 工作搭子）都能直接读懂、改写 md，不需要 API 协议 |
| **人类可读可改** | 没有二进制黑盒，出事了自己用记事本就能修 |
| **工具无关** | 前端、Agent、定时脚本可以独立替换，只要都遵守同一份格式 |
| **离线优先** | 一个 `.md` 文件，断网也能读能写，不需要后端服务器 |
| **版本可控** | 丢进 git 就能 diff / 回溯 / 审计，天然抗数据丢失 |
| **易于桥接** | 想要日历/任务能力时，写一个「md → 目标格式」的转换脚本即可（本项目已附 `scripts/parse_kanban.py` 做 md→CalDAV 的示范） |

**对你 CalDAV 场景的映射：**

```
自然语言/随手记  ──►  md 看板(意图层)  ──►  转换脚本  ──►  CalDAV(执行/同步层)
   (工作台/AI)       唯一事实源            (bridge)        (你的日历工具)
```

md 负责「人想做什么」，CalDAV 负责「日历里真的有什么」。两者之间只用一个转换脚本解耦，**谁都不用理解对方的实现**。这正是这个模式最值钱的地方。

> ⚠️ 但要清醒它的边界（见第 6 节）。它不是银弹：实时性、并发写入、双向冲突这些坑都得正视。这个模式适合「个人 / 小团队、低频写、明确单一写入者」的场景——你正好是这样。

## 2. 核心架构：三个角色 + 一份文件

```
        ┌─────────────┐        读/写         ┌──────────────────────┐
        │  人类 / 前端  │ ───────────────────►│                      │
        │ 工作台.html  │                     │   工作搭子看板.md     │
        └─────────────┘ ◄───────────────────│   （唯一事实源）      │
                 读/写                      │                      │
                                            └──────────┬───────────┘
                                                       │ 读
                       ┌───────────────────────────────┼──────────────────────────┐
                       │ 写                            │ 读                        │ 读/写
                       ▼                               ▼                           ▼
                ┌─────────────┐              ┌────────────────┐          ┌────────────────┐
                │ AI Agent     │              │ 定时解析器      │          │ 你的 CalDAV    │
                │ 工作搭子      │              │ parse_kanban.py│          │ 日历工具        │
                │ 自然语言→结构化│              │ 每天/cron 触发 │          │ (执行层)        │
                └─────────────┘              └───────┬────────┘          └───────┬────────┘
                                                    │ PUT/ICS                  │ 双向同步
                                                    └──────────────────────────┘
```

**角色职责边界（关键设计原则）**

- **文件是唯一事实源**：所有「当前状态」只在 `工作搭子看板.md` 里。任何角色都从它读、向它写，不各自存私货。
- **前端（工作台.html）**：只负责录入 + 展示 + 本地缓存（localStorage 是离线的副本，不是权威）。它通过「同步」按钮与 md 文件交换数据。
- **AI Agent（工作搭子）**：负责「把自然语言变成结构化任务」「排优先级」「生成每日提醒」。它读写的是同一份 md。
- **定时解析器（你的 CalDAV 工具）**：只负责「读 md → 在日历里创建/更新任务」。它不决定优先级，只忠实搬运。

> 把「决策（写什么）」和「执行（搬到哪）」拆开，是这套架构能复用的最大原因。

## 3. 数据格式规范（最重要，拿来就能写 parser）

文件分三个区块，用 `## 标题` 区分。**键名固定、字段顺序可变**，缺省字段可省略。

### 3.1 待办（任务）

每行一条，格式：

```
- [ ] [高] 任务描述 | id:k-l3k4j5 | 截止:2026-08-18 | 预估:3 | 项目:职称评审 | 顺延:0
- [x] [中] 已完成任务 | id:k-m2n3p4 | 截止:2026-08-17 | 预估:1 | 完成:2026-08-17
```

| 片段 | 含义 | 取值 | 必填 |
|------|------|------|------|
| `- [ ]` / `- [x]` | 完成状态 | 空格=未完成，x=完成 | 是 |
| `[高]/[中]/[低]` | 优先级 | 高>P0，中>P1，低>P2 | 是 |
| 第一段文本（首个 `|` 前） | 任务标题 | 任意文本 | 是 |
| `id:<稳定ID>` | 任务唯一标识 | 由工具生成，形如 `k-<时间戳36进制>-<随机>` | 是（由工具写入） |
| `截止:<YYYY-MM-DD>` | 截止日期 | 日期，可空 | 否 |
| `预估:<数字>` | 预估工时（小时） | 数值，可空 | 否 |
| `项目:<项目名>` | 关联项目 | 项目区块里的名字，可空 | 否 |
| `顺延:<次数>` | 顺延计数 | 整数，默认 0 | 否 |
| `完成:<YYYY-MM-DD>` | 完成日期 | 仅完成时带 | 否 |
| `日历:<事件UID>` | 关联日历事件 | events.md 里该事件的 uid | 否 |

> ⚠️ **`id` 不可用行序代替**（2026-10-19 修复的真实 bug）。
> 早期实现用「行序」当 id（`t0`/`t1`/`t2`…），而新建任务会插入到队首，
> 导致所有存量任务的 id 整体错位——删 A 会连带删掉 B 的日历事件。
> 任何按 id 定位任务的逻辑（解析、更新、删除、解绑）都必须读 `id:` 字段；
> 对没有该字段的旧文件，行序仅作为读取时的兼容回退。
>
> `日历:<uid>` 与 events.md 里该事件的 `kanbanTaskId` 互为反向引用，两者共同构成
> 「任务 ↔ 日历事件」的双向绑定。删任务或删事件时按此字段级联。

**解析正则（Python 参考，与前端 `fromKanbanMD` 等价）：**

```python
import re
m = re.match(r'^-\s*\[([ xX])\]\s*\[([高低中])\]\s*(.+)$', line)
# m[1] -> done 标记; m[2] -> 优先级; m[3] -> 剩余内容
# 剩余内容按 '|' 切，第一段是标题，后面每段 "键:值" 拆字段
```

### 3.2 项目（跟进）

```
### 职称评审
当前：论文修改中
下一步：定稿后上传平台填写信息
卡点：无
关联：改出职称评审论文, 职称评审平台信息填写完整
```

| 行 | 含义 | 说明 |
|----|------|------|
| `### 项目名` | 项目标题 | `### ` 开头 |
| `当前：` | 当前进度 | 任意文本 |
| `下一步：` | 下一步动作 | 任意文本 |
| `卡点：` | 阻塞点 | 写 `无` 表示不卡 |
| `关联：` | 关联任务 | 逗号分隔的任务标题，与待办区块通过文字匹配关联 |

> 注意：项目与任务的关联是靠**任务标题文字匹配**实现的，不是靠 ID。好处是人类手写 md 也能关联；代价是改名会导致关联断掉——这是「人写友好」换来的一个小代价，可接受。

### 3.3 速记（灵感）

```
- #标签1 #标签2 灵感内容文字
```

`#` 开头的是标签，其余是内容。一行一条。

### 3.4 序列化规则（object → md）

写回 md 时务必遵守：
1. 顶部 `# 工作搭子看板` + `> 最后更新：<ISO8601>`。
2. **已完成任务保留在待办区块、标 `[x]` 并带 `完成:`**，绝不删除（否则历史统计会失真）。
3. 字段按「标题 | 截止 | 预估 | 项目 | 顺延 | 完成」顺序拼接，省掉空字段。
4. 用**原子写**：先写临时文件再 `rename` 覆盖，避免写到一半程序崩了把文件写坏。

## 4. 集成模式（三种，给你抄）

### 模式 A：第三方 AI Agent 处理 md（你已经有了）

任何能读文件的 AI 都能当「工作搭子」：让 Claude Code / Cursor / 你自己的脚本读取 `工作搭子看板.md`，根据用户随手发的消息，把新任务按第 3 节格式**追加写回**同一个文件。

- **触发**：你主动把消息喂给 Agent，或 Agent 监听一个「收件箱」md。
- **要点**：约定「只追加、不动别人的行」，避免覆盖。
- **本包示范**：`work-dazi/agents/work-dazi.md` 就是这个 Agent 的角色定义。

### 模式 B：定时解析 → 创建日历任务（你的 CalDAV 工具主战场）

用 cron / 系统定时任务，每天固定时刻跑一次解析器，把 md 里的任务同步进 CalDAV。

```bash
# 每天 08:55 把当天/逾期未完成任务推到 CalDAV
55 8 * * 1-5  python3 /path/to/parse_kanban.py \
    --push \
    --url "https://your-caldav.example.com/calendars/user/tasks/" \
    --user "yourname" --pass "$CALDAV_PASS" \
    /path/to/工作搭子看板.md
```

- **触发**：cron / systemd timer / WorkBuddy 自动化。
- **要点**：用**稳定 UID**（见第 5 节）保证重跑幂等——同一任务不会在日历里变成两条。
- **增量策略**：建议「只同步未完成任务」「md 删了的任务，在 CalDAV 里标 COMPLETED 而非硬删」，保留可追溯性。

### 模式 C：手动同步（即时触发）

工作台里的「↻ 同步到工作搭子 / ↻ 从工作搭子同步」按钮，以及直接跑一次解析器，都属于手动同步。适合「我现在就要让日历反映刚写的计划」的场景。

> 三种模式可以共存：平时 Agent 维护 md，cron 每天搬运，你想立刻生效时手动跑一次。

## 5. 参考解析器 `scripts/parse_kanban.py`

纯标准库实现，**无任何第三方依赖**，断网可跑。它做了三件事：

1. 解析 `工作搭子看板.md` → 任务对象（严格按第 3 节 grammar）。
2. 生成标准 **iCalendar (ICS / VTODO)**。
3. （可选）用 `curl` 把每条任务 `PUT` 到你的 CalDAV 日历集合。

**用法：**

```bash
# 1. 仅解析并打印（调试 / 看效果）
python3 parse_kanban.py samples/工作搭子看板.md

# 2. 生成 ICS 文件
python3 parse_kanban.py samples/工作搭子看板.md --ics out.ics

# 3. 直接推到 CalDAV（需 curl + 账号）
export CALDAV_PASS='xxxx'
python3 parse_kanban.py samples/工作搭子看板.md \
    --push --url "https://your-caldav/calendars/user/tasks/" \
    --user yourname
```

**幂等性（最重要的一行）：**

```python
# 用任务标题派生稳定 UID，重跑时覆盖同一文件，不会重复创建
uid = uuid.uuid5(uuid.NAMESPACE_URL, 'kanban/' + task['text']).hex
# PUT 到  {url}/{uid}.ics
```

> 你自己的 CalDAV 工具如果只是「读 md 自己建任务」，逻辑一样：**给每条任务一个稳定且唯一的 key（标题哈希 / 你自己的 ID），创建前先查是否已存在**。

## 6. 踩坑与最佳实践（诚实版）

这套模式小项目很好用，但下面这些坑不提你会踩：

1. **并发写入竞争**
   两个角色同时写同一个 md → 后写的覆盖先写的，丢数据。
   ✅ 对策：明确**单一写入者**（比如只让 Agent 写，定时脚本只读 + 另存）；或加文件锁；或写临时文件再 `rename`（原子写）。

2. **格式漂移**
   md 是「人也能改」的，人一改就容易破坏 parser 假设。
   ✅ 对策：固定 schema（第 3 节）+ parser 严格校验 + 保留 `samples/工作搭子看板.md` 当测试夹具 + 改 parser 时跑一遍样例。

3. **非实时**
   md 变了不会自动通知日历。要么显式「同步」按钮，要么轮询，要么文件监听。
   ✅ 对策：桌面端可用 `fswatch` / `inotifywait` 监听 md 变化触发同步；移动端用「手动同步」按钮最稳。

4. **CalDAV 删除语义**
   md 里删了一条任务，CalDAV 里要不要删？硬删会丢掉历史。
   ✅ 对策：md 删除 → CalDAV 标 `STATUS:COMPLETED` 或 `TRANSP:TRANSPARENT`，保留记录。

5. **双向同步冲突**
   既想「md 改了同步到日历」，又想「日历里勾掉了同步回 md」，两边都改就可能有冲突。
   ✅ 对策：定义**主从关系**——以 md 为权威（Source of Truth），日历是下游镜像；反向只同步「完成状态」这一种轻量信号，避免全量双向合并的复杂度。

6. **二进制 / 附件**
   md 不适合存图片、文件。
   ✅ 对策：附件外链或单独目录存，md 里只留路径/链接。

7. **大文件性能**
   单一 md 攒几千条后会变慢、易冲突。
   ✅ 对策：按「每日一个 md」或「每项目一个 md」分片；解析器支持 glob 多个文件。

8. **时区**
   截止只存 `2026-08-18`（本地日期），CalDAV/iCal 需要明确时区。
   ✅ 对策：生成 ICS 时按你的时区补 `TZID`，或统一用 `DUE;VALUE=DATE` + 约定本地日。

## 7. 扩展方向

- **git 版本化**：把 md 丢进 git 仓库，每次同步 commit 一次，天然有「时间线 + 回溯 + 审计」。
- **多文件分片**：`inbox/`、`projects/`、`daily/2026-08-18.md`，parser 支持 glob。
- **加密**：敏感任务用 `gpg` 加密 md，Agent 解密后再处理。
- **更多后端**：同一份 md 可以同时桥接到 飞书 / Notion / 邮件 / Todoist，每个写一个轻量 bridge 即可。
- **反向同步**：让 CalDAV 事件变更回写 md（见第 6.5 节主从约定），实现「在手机日历勾掉 → 工作台也显示完成」。
- **自然语言入口**：已经做了——工作台录入 + Agent 解读，相当于给你的 CalDAV 加了一个「说话就能建任务」的入口。

## 8. 快速开始（对你自己的 CalDAV 工具）

1. **确定映射**：md 的「待办」→ CalDAV 的 VTODO（任务清单）还是 VEVENT（日程）？通常待办映射到任务、带具体时间的映射到日程。
2. **复用格式**：直接采用第 3 节的看板格式，或自己定义一套、改 `parse_kanban.py` 的解析正则即可。
3. **接 CalDAV**：把 `--url/--user/--pass` 换成你日历工具的 CalDAV 集合地址，先 `--ics` 本地验证格式，再 `--push` 实测。
4. **接 AI**：把你常用的 Agent 指向这份 md，告诉它「按格式追加任务」，参考 `work-dazi/agents/work-dazi.md`。
5. **定个节奏**：每天一次 cron 搬运 + 需要时手动同步，就够了。

> 一句话总结这套打法：**用最朴素的 Markdown 当总线，AI 负责把混乱变有序，脚本负责把有序搬去该去的地方。** 简单、可移植、不绑定任何厂商——这正是它值得借鉴的原因。
