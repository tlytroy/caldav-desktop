## 阻断问题（4）

### R1 [P1 / 可用性] 恢复 marker 存在时没有逃生路径；pinned 过期后应用永久停在 maintenance

**证据**
- SDS:536-545 的恢复状态机在写 `restore-in-progress.json` 后置 `maintenance=true`；SDS:561-564 规定启动时若存在 marker，则“不自动恢复；maintenance=true；暂停自动同步”，并声称“pinned 失效时提示重新预览”。
- 但 SDS:526 规定 preview 生成的 pinned 副本 24h 后清理，restore 缺失即 409 `RESTORE_SNAPSHOT_EXPIRED`；SDS:554-555 的 maintenance allowlist 只有 `restore/status/health/overview`，**不含 preview**；`POST /api/workspace/backups/preview` 在 SDS:500-517 是 POST，按 SDS:554 的“所有 mutating /api（POST/PUT/PATCH/DELETE）”会被 503。SDS:560 又说 `POST /api/sync/resume` 在恢复窗口内不可用。
- 结果：崩溃 + marker 残留 + pinned 超过 24h（或 pinned 被清理）时，retry restore 永远 409，重新 preview 被 503，resume 被 503；没有 abort/clear-marker 接口，也没有启动时“pinned 不存在则自动清 marker”的策略。用户只能手工删除 `restore-in-progress.json`，否则所有写操作永久 503。这与“崩溃各阶段都可恢复”的承诺冲突。

**影响**：恢复功能在最需要它的故障场景下把应用锁死；属于可用性/可运维性阻断。

**契约级修复**
- 将只读的 `GET backups`、`POST backups/preview`、`GET backups/export` 加入 maintenance allowlist（preview 只写 `.pinned`，不写 workspace；只读模式下可拒绝 pin 但返回 diff/sha 的计算结果，或明确提示“无法 pin”）。
- 增加 `POST /api/workspace/backups/restore/abort`（需 token）：清 marker、`setSyncMaintenance(false)`、保留 `.pre-restore-*` 与 `sync-suspended`，返回当前状态；UI 在 retry 409 时提供该入口。
- 定义启动策略：marker 存在但对应 pinned 缺失/过期时，自动清 marker 并恢复维护标志（或进入显式的“restore-pending”只读页，提供 abort），不得要求手工删文件。
- S18 增加“pinned 过期 + 崩溃 + 重启”用例，断言有可达的 abort/重试路径。

### R2 [P1 / 数据] `waitForInFlightSync` 只覆盖 CalDAV；in-flight 的 WebDAV pull/merge 可在恢复完成后回写

**证据**
- SDS:270-273 明确“`caldav-sync.ts` 的私有 `inFlight` 由该模块登记”，SDS:540 的恢复 drain 只调用 `waitForInFlightSync(10_000)`。
- WebDAV pull/merge 是普通 HTTP 路由：`apps/server/src/routes/webdav.ts:394-424`（pull 先网络下载，再 `writeFileSync`）、`apps/server/src/routes/webdav.ts:460-505`（merge 先 `putRemoteFile`，再 `writeFileSync`）；SDS:556-557 只要求“入口检查”sync-suspended，SDS:273 的 epoch 检查写在“每个 sync”里，WebDAV 路由不在该 in-flight 集合内。
- 竞态：WebDAV pull 在恢复前通过入口检查并开始下载；恢复置 maintenance、drain 立即返回 true、拿锁覆盖 workspace；随后 pull 的写拿到锁，把远端旧文本写回，**覆盖刚恢复的数据**。merge 同理会把恢复前的合并版 PUT 到远端，再在本地 409，造成远端与恢复结果分叉。

**影响**：恢复的最坏结果——用户以为已恢复，几秒后被在途请求覆盖；属于数据完整性阻断。

**契约级修复**
- 把 WebDAV pull/merge（以及任何“读远端→写本地”的路由）登记进 `sync-control` 的 in-flight 集合；`waitForInFlightSync` 等待 CalDAV + WebDAV 全部结束。
- 或在 `mutateWorkspace`/`mutateWorkspaceText` 的提交点统一检查 `isSyncMaintenance()` + restore generation（不是只在每个 sync 调用点检查），使恢复窗口内任何本地提交都失败并返回 `SYNC_EPOCH_ABORTED`。
- S10/S17 增加：延迟远端响应 → 触发 restore → 断言 pull/merge 不落本地、远端不被旧合并版覆盖。

### R3 [P1 / 安全] `%61pi` 编码前缀绕过 `/api` auth；S7/S16 的验收无法按 SDS 顺序通过

**证据**
- SDS:352-383 的顺序是 `app.use("/api", auth)` 在 static/SPA 之前，并断言“静态目录若含 `api/...`，此时 auth 已挂载，不会公开 `/api` 路径”；SDS:383 要求测试 `%61pi`、`/api//`、static 下 `api/x`；SDS:685（S7）明确要求 `%61pi` 用例，SDS:694（S16）要求 `/API` 返回 401。
- Express 4 的 `app.use("/api")` 用 `req.url` 的原始 pathname 匹配，`/%61pi/...` 不会命中 `/api` 中间件；随后 `express.static` 对路径段做 `decodeURIComponent`，`/%61pi/...` 会被解析为 `/api/...`。若 `staticDir/api/x` 存在，该文件将**未经 auth** 被返回；若不存在，SPA fallback 看到的仍是 `/%61pi/...`，会返回 `index.html` 200，而不是 S7 期望的 401。
- 这不是“/API 大小写”问题（那部分 SDS 已处理），而是编码规范化问题；SDS 没有对应的拒绝/规范化中间件。

**影响**：当前 renderer 构建没有 `api/` 目录，所以不是现成的 API 数据泄露；但 SDS 自己的安全断言与 S7/S16 验收不成立，且未来构建一旦出现 `staticDir/api/*` 即为未认证静态暴露。按“验收必须可执行”的标准，这是阻断。

**契约级修复**
- 在 auth 之前增加路径规范化/拒绝：对 pathname 先做一次 `decodeURIComponent`（或逐段解码）后再匹配 `/api`；含编码斜杠/编码 `api` 的请求直接 400/404，禁止进入 static。
- 或把静态资源挂到独立前缀（如 `/static`），并禁止 static 根下出现 `api/`；SPA fallback 同样用规范化后的路径判断。
- 明确 `%61pi`、`%2f`、`/api//` 的期望状态（401 或 404，不能是 200 HTML），并让 S7/S16 断言该状态。

### R4 [P1 / 数据] WebDAV merge 仍是“先 PUT 远端、后 commit 校验”；且未定义 frontmatter/unknown/rawBlock 的合并

**证据**
- SDS:299-320：`prepareMerge` 取 `baseHash` 与 `mergedText` 后释放锁；步骤 2 锁外 `PUT`；步骤 3 才 `commitMerge`；步骤 4 却要求“合并文本 parse/图校验失败 → 409 `MERGE_INVALID`，本地不动；不覆盖远端”。PUT 已经发生，“不覆盖远端”在该顺序下不可能成立。
- `commitMerge` 内部调用 `mutateWorkspaceText`（SDS:307-313），而 SDS:147-149 规定 `mutateWorkspaceText` 在写前做 tolerant parse + 图校验；一旦该校验失败，异常发生在 PUT 之后，远端已是合并版、本地仍是旧版，SDS 没有定义补偿、事件或用户可见的 remote hash。
- `mergeWorkspaceText`（`apps/server/src/routes/webdav.ts:137-180`）当前只解析出 items、过滤 `!errors`、按 `updatedAt` 取并集后 `serializeWorkspace`；它不携带 `frontmatterRaw`、`unknownBlocks`、`extra`、`rawBlock`。SDS:204-238 的 round-trip 契约没有说明 merge 写路径如何保留这些内容，因此 D27 的合并可能丢掉远端独有的未知块/字段，或把本地 frontmatter 降级。

**影响**：远端/本地在失败路径分叉；合并写路径破坏 round-trip，属于数据完整性阻断（尤其在用户用 merge 解决冲突时）。

**契约级修复**
- 把 mergedText 的 parse + `validateWorkspaceGraph` 前移到 `prepareMerge`（PUT 之前）；PUT 前失败直接 409，远端不动。
- 明确 merge 的三方输入是 `WorkspaceFile`（含 `frontmatterRaw`/`unknownBlocks`/`extra`/`rawBlock`）：frontmatter 采用“本地优先、远端 v2 不降级”的确定规则；unknown 块按块合并（至少本地 + 远端独有块并集）；`rawBlock` 条目原样保留。若 v0.3 不做，明确列为限制并给用户提示，不能静默丢弃。
- 若 PUT 成功后 `commitMerge` 仍失败，记录冲突事件并返回 `remoteEtag` + `remoteHash`，UI 只允许“重新合并”，不得显示“本地/远端均未变”。
- S12 增加：远端 v2 frontmatter + 未知块 + 坏条目、本地未知块，断言 merge 后全部保留；以及“PUT 后 commit 失败”的分支。

## 非阻断问题

1. **N1 `createApp` 的 token 边界仍偏 fail-open**：SDS:352-359 只拒绝 `token === ""`；`undefined` 表示“v0.2.5 无认证”，`" "`/短串也不会被拒。v0.3.0 的 `index.ts` 若漏传 token，所有 `/api` 静默开放。建议改为显式 `auth: false` 才允许无认证，v0.3.0 路径要求 64hex，并加 `createApp({})`/`{token:" "}` 的负向测试。
2. **N2 plan 与 SDS 的 createApp 顺序矛盾**：`docs/planning/v0.3-plan.md:31` 仍是 `static → /api auth`，SDS:352-383 是 `auth → static`。SDS 的顺序更安全，但必须同步修订 plan A1/§4.2，否则 P1 按 plan 实现会把 B1 带回来。
3. **N3 只读模式没有端到端闭合**：SDS:177-203 只在“mutating API”层 503；`mutateWorkspace`、`writeSyncState`、scheduler 的 `writeState` 没有 `storageReadOnly` 检查。`startCalDAVAutoSync()`（`apps/server/src/caldav-sync.ts:1051`）与 `startReminderScheduler()`（`apps/server/src/index.ts:114`）仍会启动；在真只读 `/data` 上会周期性尝试写、刷日志，CalDAV 还可能在推送远端后本地落盘失败。建议在 store/sync-control 层统一拒绝，并在只读时跳过这两个 timer（或让 tick 直接 no-op）。另外 `preview` 需要写 `.pinned`，只读 `/data` 下 M3a 的“预览”不可用，SDS 只承诺“备份列表可用”，需在 UI/文档写明。
4. **N4 恢复没有停 reminder scheduler**：SDS:538-544 只 `stopCalDAVAutoSync()`；`apps/server/src/notifications/scheduler.ts` 的 tick 仍会读 workspace、推送、写 `.reminder-state.json`，与恢复的 sent 交集重置竞争，并可能对即将被恢复删除的条目发提醒。建议恢复期间 stop/pause scheduler，或在 `runReminderCheck` 加 maintenance/epoch 检查。
5. **N5 恢复后自动同步不会自己恢复**：`stopCalDAVAutoSync()` 清了 interval；SDS:558-560 说 `POST /api/sync/resume` “由 UI 触发对应同步”，但没写是否 `startCalDAVAutoSync()`。若不重启 interval，自动同步会静默停到下次进程重启。明确 resume 后重启 timer（或下次启动重启）。
6. **N6 `validate:"changed"` 未覆盖删除父条目产生的孤儿**：SDS:246-252 只检查“被改条目”的 parent 存在；删除一个有子条目的 parent 时，children 不在 `onlyIds`，不会被发现，留下孤儿。把被删除 id 纳入 changed 集合并检查其直接子条目，或明确 UI 禁止/级联。
7. **N7 `rawBlock` 与 `errors` 的边界未定义**：SDS:204-218 说“部分坏保留 errors+rawBlock”，SDS:220-238 说“解析失败条目保留 rawBlock”。若一个条目只是 `due` 非法（有 errors 但可解析），序列化会把 `due` 丢掉；下次无关写入即静默丢字段。需规定：凡 `errors.length>0` 的条目都保留可逆原文（或字段级 raw），修改该条目时才允许重写。
8. **N8 备份文件名同毫秒碰撞**：`apps/server/src/workspace.ts` 的 `backupCurrent` 用 `toISOString().replace(...)` 做文件名；同毫秒两次写会覆盖同一备份。加随机后缀，并把 `MAX_BACKUPS` 从 10 改到 20 的测试补上。
9. **N9 `mergeWorkspaceText` 的 `extra/rawBlock` 未覆盖**：即使 R4 只修 frontmatter/unknown，item 级 `extra` 与 `rawBlock` 也必须在合并中保留；否则“未知字段 round-trip”只在普通写路径成立。
10. **N10 损坏 token + 只读 `/data` 会拒绝启动**：SDS:333-338 的 fail-closed 正确，但与 D28“只读也继续启动”冲突；需在文档/错误信息中给出 `API_TOKEN` 逃生，或允许“只读 + 内存 token + 打印一次”启动（并说明 token 每次重启变化）。
11. **N11 Electron token 仍在 server 子进程 env 中**：SDS 只承诺“不进 renderer argv”；`fork(..., {env:{API_TOKEN}})` 对同 uid 进程的 `/proc/<pid>/environ` 可见（单用户桌面可接受）。可在文档中写明边界，或改用 stdin/一次性文件传递。

## 五条结论

1. v0.2 在读取语义、唯一写入口、锁、原子写、round-trip、token 生命周期、Electron 打包、Docker 只读启动上，已从“口号”落到可执行契约，前次 10 个阻断大多关闭。
2. 但恢复状态机仍有两处 P1：过期 pinned 后无 abort/清 marker 的逃生路径（R1）；drain 只等 CalDAV，在途 WebDAV pull/merge 可在恢复后回写（R2）。
3. 认证的 `/API` 大小写已修，但 `%61pi` 编码前缀未规范化，S7/S16 的验收按当前顺序无法通过（R3）。
4. WebDAV merge 仍是“先 PUT 后校验”，且未定义 frontmatter/unknown/extra/rawBlock 的合并，违反 round-trip（R4）。
5. 修完 R1–R4，并补上 T1/T2/T3/T5 的测试后，可转“通过”；其余 N1–N15 为非阻断，但 N1/N3/N4/N12 应在 P1/P3/P6 内一并处理。
