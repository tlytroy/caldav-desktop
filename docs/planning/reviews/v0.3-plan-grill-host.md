# v0.3 计划 Grill 记录（v0.1）

> 对象：`docs/planning/v0.3-plan-draft.md`
> 方式：主持人逐条拷问 + 独立红队 subagent（结果待回填）
> 结论状态：**未通过，需先补齐决策与两个设计缺口**

## 一、致命问题

### G1 认证的「未配置 token 只允许本机」不可行（P0）

计划写：「未配置 token 时仅允许本机访问（校验 `req.ip` 属于 loopback）」。
失败场景：

1. **反向代理**：nginx / Caddy 与后端同机时，所有外部请求的 `req.ip` 都是 `127.0.0.1`。
   没有 `trust proxy` 配置，等于对公网完全开放；配了 `trust proxy` 又可能被伪造
   `X-Forwarded-For`（取决于代理是否覆盖该头）。
2. **浏览器 CSRF / DNS rebinding**：恶意网页可以 POST 到 `http://127.0.0.1:3001`，
   浏览器发出的连接源 IP 就是本机；服务端按 loopback 放行 → 任意网站可改日程。
3. **Electron**：当前 `apps/desktop/main.ts` 用 `file://` 加载页面，请求后端属于跨源，
   `cors()` 收紧后会被浏览器拦；而 `Origin: null` 放开又等于给本地任意文件访问权。

**必须改为其中之一：**
- A. **始终要求 token**：桌面端首次启动生成随机 token（写入 `/data/.api-token` 或 config，
  0600），Electron 通过 preload / 环境注入；Docker 必须配置 `API_TOKEN` 才启动。
- B. token 只保护「非本机」，但必须校验 `Origin` / `Sec-Fetch-Site`，并只监听
  `127.0.0.1`（Docker 例外，强制 token）。

推荐 A：行为确定、不依赖 IP 判断；代价是 Electron 要能拿到 token（方案见 SDS）。

### G2 token 的引导、存储、轮换没有设计（P0）

- Docker 首次启动 token 从哪来？打印到日志会被日志系统留存；写进 config 又被掩码，
  用户之后看不到。
- 桌面端用户怎么知道 token？如果要求手填，会直接劝退。
- token 泄露后如何轮换？轮换后其他设备怎么更新？

计划里只有「存 localStorage」一句，**不足以实施**。SDS 必须明确：
启动参数 / 环境变量 / 首次生成 / 显示一次 / 重置接口 / 多设备输入方式。

### G3 并发锁只覆盖「路由里的写」，漏掉同步写入（P0）

证据：`apps/server/src/routes/webdav.ts:422`（pull 直接写文件）、`:505`（merge 直接写文件）、
`apps/server/src/caldav-sync.ts:950`（pull 后 `writeWorkspace`）。
如果只在 `routes/workspace.ts` 的 CRUD 外面加锁，**同步任务仍可与用户编辑交叉**，
后写覆盖先写，E2 的核心目标没达成。必须有一个统一的 `withWorkspaceLock()`，
所有写入方（CRUD / CalDAV / WebDAV / 迁移 / 恢复）都走它；并明确锁的粒度与超时。

### G4 原子写在 NAS 文件系统上的语义未验证（P1）

`fsync + rename` 在 ext4 成立；在 SMB / NFS / 群晖某些卷上：
- rename 可能不是原子替换；
- fsync 可能被忽略；
- 临时文件可能残留。

计划把「原子写」当作确定能力，验收却只写「模拟中断」。需要：
- 明确支持的存储类型（本地磁盘 / Docker volume / SMB）；
- 写入失败时的回退策略（保留旧文件 + 报警）；
- 在真实 NAS 上做一次手工验证（列入 DoD）。

### G5 备份恢复是破坏性操作，缺预览与二次确认（P1）

计划只写「恢复前自动备份」。用户点错一次就会把当前数据换掉。至少要有：
- 恢复前展示「当前 vs 备份」的条目数、时间、差异条数；
- 输入确认 / 二次确认；
- 恢复后给出 diff（新增/删除/修改各多少）；
- 支持「导出备份文件」再离线保存。

### G6 迁移框架是 YAGNI，且自动改写与「本地优先/用户文件」冲突（P1）

当前字段全是可缺省的，没有必须 v2 的变更。引入 `schema: workbench/v2` + migrations：
- 增加实现与测试面；
- 自动改写用户文件（即使有备份）与「不主动动用户数据」原则冲突；
- 旧版本客户端读到 v2 可能行为不明。

建议：本阶段只做**版本号检测 + 显式升级入口**（用户点「升级格式」才写），
不自动迁移；把 migrations 框架推迟到第一次真正破坏兼容时再做。计划应删掉「自动迁移」。

### G7 CalDAV 删除传播风险被低估（P1）

- tombstone 生命周期（多久清理）、uid 复用、重复事件例外实例（RECURRENCE-ID）都未定义；
- 多设备场景：A 删除 → push DELETE；但 B 离线期间又改回来 → 冲突如何处理？
- 服务端对象可能已被别的客户端删除，DELETE 返回 404 应视为成功；
- 必须是「默认关闭 + 仅删除 etag 匹配且 tombstone 存在」的对象。

建议：v0.3.0 不做，v0.3.1 单独 SDS；计划里 D4 默认 B。

### G8 WebDAV 自动同步引入新的竞态（P1）

- 自动 pull 会覆盖本地正在编辑的文件（当前 pull 只在远端变化时覆盖，仍可能撞上用户刚保存）；
- 自动 push 与 CalDAV 自动同步同时跑，两个定时器都写 workspace（E2 锁可缓解，但语义仍乱）；
- 需要「单飞」：同一时刻只允许一个同步任务；自动同步失败要退避，不能每 30s 重试风暴；
- 需要「本地有未同步修改时，自动 pull 先备份并提示」而不是静默覆盖。

### G9 同步历史/提醒状态文件的生命周期未定义（P2）

`.sync-history.json`、`.reminder-state.json`、`.webdav-state.json`、`.caldav-sync-state.json`
都是「可重建缓存」，但计划没有：容量上限、清理策略、损坏时行为、是否随备份一起恢复。
至少要在 SDS 里统一「状态文件规范」。

### G10 范围与工期明显低估（P2）

E1+E2+E3 的 7–11 人日不含：
- 认证前端（登录/令牌输入/401 全局处理/Electron 注入）；
- 同步中心新模块 UI + i18n；
- 备份恢复 UI；
- 并发/崩溃/代理/CORS 的测试基建；
- 文档与 Docker 回归。

按目前代码风格（每功能必带测试与中文文档），实际更接近 **12–18 人日**。
计划应把 UI/测试显式列进每个 Epic 的范围，而不是隐含。

### G11 验收标准仍有不可测项（P2）

- 「未授权无法读写 API」→ 哪些路径公开？`/health`、静态资源、`/api/plugins`？
- 「并发写不丢数据」→ 并发多少？通过 HTTP 还是直接调用？
- 「冲突历史可查」→ 存哪里、保留多少、如何触发？
- 「本地优先回归」→ 具体关掉哪些服务、验证哪些页面？

每条都要给出「命令 / 请求 / 期望响应」，否则实施阶段会各写各的。

### G12 流程本身的风险（P2）

- 新会话实施时**没有当前对话上下文**，SDS 必须自包含：现状、文件路径、接口、错误码、
  测试数据、验收命令，否则实施 agent 会重新发明。
- `grill-me` / `superpower` 在当前会话不可用（见下）；流程依赖不可用工具会卡住。
- 计划阶段的「独立评审」如果只读计划、不读代码，容易给出正确但空泛的意见；
  评审 prompt 必须要求引用具体文件/行号与失败场景。
- 多轮评审容易无限循环，需要门禁：每轮只允许「通过 / 有条件通过（≤5 条）/ 不通过」，
  条件必须可验证。

## 二、与现有架构的冲突 / 含糊

| 计划表述 | 冲突点 |
| -------- | ------ |
| 「自动迁移」 | 违反「不主动改写用户文件」与本地优先；应改为显式升级 |
| 「未配置 token 仅本机」 | 与 `cors()`、Electron `file://`、反代现实冲突（G1） |
| E3「同步中心」新模块 | 现有模块注册在 `modules/index.ts`；需明确是否替换日历页工具栏入口，避免两个入口 |
| E2「写入前校验 parent 存在」 | 与现有「删父任务级联删子任务」有交互：级联删除时子任务先删还是先校验？需定义顺序 |
| 「状态文件可重建」 | E3 历史 / E4 提醒状态没有容量与清理策略（G9） |

## 三、范围与顺序建议

如果只能做三件：

1. **E1 认证**（但必须先解决 G1/G2，采用「始终 token + Electron 注入」）
2. **E2 原子写 + 统一写锁**（砍掉迁移框架；只保留崩溃安全与备份恢复）
3. **E3 同步中心 + WebDAV 自动同步**（砍掉删除传播）

砍掉/推迟：

- CalDAV 删除传播 → v0.3.1（单独 SDS）
- 迁移框架 → 等第一次破坏兼容
- E4 提醒完整化 → v0.3.1
- E5 → v0.4
- E6 CI 修复 → **前置**做（0.5 人日），否则后续每次提交都在坏 CI 上跑

排序：E6（CI）→ E1（认证）→ E2（数据）→ E3（同步中心）。CI 先修是因为它成本最低、
且能保护后面所有改动。

## 四、可测试验收（补充）

1. 未带 token 请求 `/api/workspace/items` → 401；带正确 token → 200。
2. 配置 `API_TOKEN` 后，从非 loopback 直接访问（模拟 `Host`/IP）→ 401。
3. 反代模式（设置 `TRUST_PROXY=1`）下，伪造 `X-Forwarded-For` 不能绕过 token。
4. 前端 401 → 弹令牌输入 → 输入后恢复；刷新仍保持。
5. Electron `file://` 页面在启用认证后仍能正常调用 API（通过 preload 注入）。
6. 并发 50 个 POST → 全部落盘，无丢失、无重复 id。
7. 写入过程中 kill -9 / 抛错 → 重启后文件可解析，旧内容不丢。
8. 备份列表 / 恢复：恢复前后 diff 正确，恢复前自动备份存在。
9. 同步与编辑并发：CalDAV pull 与用户 PUT 同时发生 → 不丢更新（顺序可解释）。
10. WebDAV 自动同步：远端变化 → 自动 pull 前有 `.bak`；本地未同步修改时不被静默覆盖。
11. 同步中心：未配置 / 连接失败 / 有冲突 三种状态都正确展示，不 500。
12. 删除传播（若做）：只 DELETE tombstone 对应 uid，404 视为成功，etag 不匹配则报冲突。
13. `docker build` + 容器冒烟；`data/workspace.md` 可读写。
14. 本地全关服务器：日历 / 任务 / 应用内提醒仍可用（手工清单）。
