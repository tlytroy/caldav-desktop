# 独立评审 B（产品 / 运维 / 支持）— v0.3 计划 v0.2

> 评审对象：`docs/planning/v0.3-plan-v0.2.md`
> 结论：**有条件通过（5 条）**

## 1. 结论

**有条件通过（5 条）**：

1. **先消除 M3 的内部矛盾**：§M3 写「缺 `API_TOKEN` 启动失败 exit 1」，D1 写「只放行 `/health` 与静态资源」。二者只能留一个。建议选 D1，并在缺 token 时**自动生成一次性 token 写入 `/data/api-token.txt`、日志与引导页显著展示**（Jellyfin/HA 模式）。否则老 Docker 用户升级＝容器重启循环＋浏览器「无法访问此网站」，无自救入口。
2. **拆两个发布**：v0.2.5 = M1+M2+M4（数据安全，零升级摩擦）；v0.3.0 = M3+M5(+M6)。把不可逆的数据修复与破坏性的认证变更解耦。代价是 M4 集成测试在 M3 落地时补 token fixture（约半天），值得。
3. **补 M4 备份保留策略**：数量/容量上限、自动清理、「自动快照」与「手动导出」区分。目前 `.workspace-backups/` 是每次写入前备份，NAS 上日积月累后列表不可用且占盘。
4. **D15 承诺的直连模式离线体验必须在里程碑里有归属**：全局「服务器不可达」横幅 + 保存失败提示。现在只写在验收 §8.14，没有任何任务项承接。
5. **补齐迁移文档与回滚包**：DEPLOYMENT 增 v0.2→v0.3 迁移节、token 填法、忘记 token、Electron token 查看入口、升级前备份 `data/` 并保留上一个镜像 tag。

## 2. 用户价值与优先级

- **顺序**：M1 无用户感知但必须先做（0.5–1 天可接受）；M2 是唯一「不可逆损失」的修复，排第一正确。**问题在 M3 排在 M4 前**：用户先付出 token 摩擦，才拿到数据安全感。NAS+Radicale 用户多在局域网/Tailscale，暴露风险低，认证的感知价值≈0。
- **谁最减痛**：数据安全（M2+M4）≫ 同步面板（M5）> 认证（M3）。M5 是支持成本杠杆（让用户自查「为什么没同步」），但不是能力；M3 是「该做但不该先做」。
- **感知不到的投入**：round-trip 未知字段、50 并发、kill -9 测试——便宜且防事故，保留；**反代/CORS 多拓扑矩阵建议收敛**到「1 跳 Nginx + Tailscale」各一个样例，省下时间给引导页与迁移文档。M3 为少数高级用户做 3 种拓扑验收，收益/成本不匹配。

## 3. 部署与升级路径

- **Docker 老用户**：现有 compose 无 `API_TOKEN`、`env_file` 还是注释掉的；新 compose 用 `${API_TOKEN:?}`，用户 `docker compose up -d` 会直接撞一行看不懂的 `:?` 报错；用 `docker run`（DEPLOYMENT 里就这么写）则容器 exit 1 + `restart: unless-stopped` → 重启循环，healthcheck 变 unhealthy，浏览器只显示「无法访问」。两种都缺「下一步怎么办」。
- **Electron**：token 每次启动随机、只经 preload 注入。注入失败（preload 异常 / 打包路径 / contextIsolation）= 用户在自己电脑上被要求输入一个自己看不到的令牌，且**没有查看入口** → 死路。必须兜底：主进程写 token 到 userData 文件 + 菜单/关于页可复制 + 启动日志打印。回滚：手动重装旧版即可，`workspace.md` 格式未变（round-trip 只增不减），**降级安全**，但要写进文档。
- **备份恢复可理解性**：用白话「这是自动快照，恢复=把整个文件退回那一刻」；预览写「+3 新增 / -1 删除 / 2 修改」+ 标题，不用 diff 术语；二次确认须写明「手机端/云端不会自动变，下次同步可能冲突」；恢复前自动快照置顶并标「可撤销」。
- **文档缺**：迁移 3 步 + `openssl rand -hex 32`、token 填在哪（浏览器/PWA/Electron 各一句）、忘记 token（改 env 重启 + 全设备重输）、反代须透传 `Authorization`、升级前备份 + 保留旧镜像 tag。另：DEPLOYMENT 现写「后端没有内置登录，公网请套 basic auth」，v0.3 后必须改，否则用户叠两层认证。

## 4. 支持成本

**预计 Top5**：①升级后打不开 / 容器反复重启 / `API_TOKEN` 报错（计划只解决一半）；②「访问令牌是什么、在哪」（计划只有输入框，无获取路径）；③换 token 后手机 PWA 重输 / iOS 清 localStorage（未覆盖）；④反代后 401/429；⑤恢复备份后提醒重复推 / 同步把旧数据推回。

**会增加负担的设计**：PWA 直连（token + CORS + iOS 存储清理三重）、`file://` null origin 特例、token 轮换无多 token/会话管理（轮换=全员重登）、单独托管前端。**建议 v0.3 明确：浏览器端只支持后端同源托管**，单独前端托管标为高级/不支持；Electron 优先本地 HTTP 同源，尽量删掉 null origin 分支。

**具体缺陷**：
1. 限流按 IP，Nginx/Docker 后全家共用一个桶；建议明确只算 `/api/*` 不含静态，否则大日历冷启动可能撞 600/min。
2. §M4 写「清空提醒 sent」而验收 §8.9 写「旧提醒不重发」，**自相矛盾**——建议按 id 保留，只清恢复点之后新增条目。
3. `TRUST_PROXY_HOPS=0` 时所有 LAN 客户端共享代理 IP 的 401 计数，20/min 会把正输错 token 的用户锁 1 分钟，需文案。

## 5. 范围建议

- **E4/E5 延后：同意**，但计划 §3 非目标只写「不进 v0.3.0」，没说 E4/E5 是什么，评审无法验收「延后」；建议各写一行并入 backlog。
- **只交付一个：M4（含 M2 的锁/原子写作为前置）**。理由：数据丢失是唯一不可逆失败；M2 单独交付用户感知不到，M3 只增加摩擦，M5 只提升可诊断性。
- **被忽略的高价值小改动（3 条）**：
  1. 直连模式全局「服务器不可达」横幅 + 保存失败 toast（D15 已承诺，<0.5 天）。
  2. 设置/关于页显示版本、数据文件绝对路径、备份数量、`/health` 状态（复用 `/api/workspace/info`），消灭「我的数据在哪」工单。
  3. 首次打开 v0.3 的 token 页兼作「升级须知」：三行说明 + 「导出备份」按钮 + 「Docker 用户看这里」。
