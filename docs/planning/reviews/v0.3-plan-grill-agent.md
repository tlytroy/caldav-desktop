# 独立红队评审（agent 整理版）

> 评审者：独立 subagent（只读计划，未读代码）
> 对象：`v0.3-plan-draft.md`（305 行）
> 结论：**必须先补决策，不能直接进入 SDS**

## 致命问题

### 1.1 loopback 回退在 Docker / 反代下必然误判

未配 token 时按 `req.ip` 判 loopback：

- NAS Docker 端口映射：容器内看到的对端是 bridge 网关（如 `172.17.0.1`），不是 127.0.0.1
  → 按文档不配 token 会全部 401，用户很可能去放宽 `trust proxy`。
- 放宽后攻击者伪造 `X-Forwarded-For: 127.0.0.1` 即可绕过全部认证。
- `::ffff:127.0.0.1`、Unix socket、127/8 集合、代理层数都未定义。

**决策建议**：删除 loopback 回退，fail-closed —— 未配 token 时只放行 `/health`，
其余 401 并提示配置。

### 1.2 CORS 与「同源默认」在 Electron / Vite 下自相矛盾

- Electron `file://` 的 Origin 是字符串 `null`；Vite dev 与后端不同端口。
- 带 `Authorization` 的请求必触发 OPTIONS 预检：若 OPTIONS 也校验 token → 预检 401，前端全挂。
- 允许 `ACAO: null` 等于对任何沙箱 iframe 开门。
- 缺：OPTIONS 免鉴权豁免、null origin 策略、dev 端口白名单、`Vary: Origin`。

**决策建议**：CORS 只作浏览器侧防线，不承担鉴权语义；Electron 用自定义协议/本地反代
（或至少明确 null origin + 始终 token）。

### 1.3 token 引导链没设计，`/api/auth/*` 是自造爆破面

- 前端需要知道「服务端是否已配 token」，这本身泄露信息。
- `OPTIONS`/`/api/auth/*` 若豁免鉴权又接受 token 比对，就是无限速猜 token 端点。
- localStorage 多标签各一份；手机换设备要重输；Electron 注入与浏览器是两套路径。
- 缺：首次引导、轮换、清除后 401 死循环。

**决策建议**：Electron 用 `safeStorage` + preload 注入；浏览器才用 localStorage；
不设 `/api/auth/*` 这类额外端点。

### 1.4 锁的覆盖范围写的是「API」，但同步 / 调度器 / 恢复都在写同一文件

- CalDAV/WebDAV pull/push、提醒调度、备份恢复都改 `workspace.md`。
- 场景：用户点「立即同步」同时改任务 → pull 基于旧快照整体重写 → 编辑丢失；
  或同步持锁等网络 → 所有 API 排队到超时。
- 「写入前重读最新文件」只防丢更新，不防同一目不同字段互相覆盖
  （会把 CalDAV 的字段级合并退化成整条覆盖）。

**决策建议**：锁只保护「读-改-写」临界区，网络 IO 必须在锁外；
所有写路径统一走 `withWorkspaceLock`。

### 1.5 原子写在 Windows / SMB 上会退化，验收只测 Linux

- Windows 上目标被杀软 / OneDrive / 编辑器持有句柄时 rename 抛 EPERM/EEXIST。
- tmp 跨文件系统时 rename 非原子；SMB/NFS 上 rename/fsync 语义弱。
- 缺：失败重试/退避、tmp 清理、rename 失败时是否降级（降级即破坏原子性）。

**决策建议**：tmp 必须同目录；rename 重试 3 次后**报错而非降级**；
Windows + SMB 列为发布门槛。

### 1.6 备份恢复后同步 / 提醒状态全部失配

- 恢复 3 天前备份 → etag 与远端失配 → 下次同步把旧数据推回或制造全量冲突。
- `reminder sent` 对应旧条目 → 重发或永久漏发。
- 恢复若与同步并发 → 两边写同一文件。

**决策建议**：恢复 = 停调度 → 锁 → 备份 → 写 → 重置同步缓存 → 全量冲突重扫；
diff 必须在覆盖前计算并可预览。

### 1.7 迁移框架是 YAGNI，且漏掉真风险：往返丢字段

- 当前无必须 v2 的变更；E4 的 `remindChannels` 可缺省，不需要迁移。
- 真正风险是解析-序列化往返丢掉未知字段/注释/顺序，计划没提。

**决策建议**：删除迁移框架，改为「未知字段与未识别块原样保留」的 round-trip 测试 + 只读兼容。

### 1.8 墓碑既违反「状态可重建」，又搞错删除单位

- 墓碑是「删除意图」，丢了就不可重建 → 远端条目下次 pull 复活。
- CalDAV 删除单位是 **href**，同一 uid 的多个 RECURRENCE-ID 例外实例是不同 href。
  按 uid 删会误删整个系列。
- 缺：ETag 412 时是否清墓碑、过期策略、存哪。

**决策建议**：v0.3 不做；若做，键必须是 href，恢复备份时不清墓碑。

### 1.9 WebDAV 自动同步竞态与「冲突谁做主」未定义

- 定时器 + debounce + 手动同步 + 冲突三选一可并发 → 重复 PUT。
- 改间隔旧定时器未清 → 双倍频率。
- 自动同步遇冲突若自动 force/merge = 未经同意丢数据。

**决策建议**：单飞互斥；自动同步永不自动解决冲突（暂停转人工）。

### 1.10 工期与验收双失真

- 每个 Epic 都隐含大量 UI/测试：认证前端、同步中心、恢复 UI、代理/CORS 测试。
- 原估 7–11 人日，真实量级 ×2–3，合计 15–20 人日。
- 「并发 50 创建 = 50 条」只证明不丢创建，不证明不丢更新；
  「构造 tmp 文件」不等于断电测试；手工验收不可复现。

## 与「唯一事实源 / 本地优先 / 状态可重建」的冲突

| 计划表述 | 冲突 |
| -------- | ---- |
| 「状态文件只能是可重建缓存」 | 墓碑（删除意图）、`.sync-history.json`（审计）都不可重建，定义漂移 |
| 「服务器全挂不影响本地」 | 前端-only 直连 NAS 时本地无副本，后端挂 = 空白；「本地优先」在该形态是假的 |
| 「一个数据文件」 | 备份目录 / 同步历史是第二份持久数据；恢复是事实源替换，未定义「恢复期间谁是事实源」 |
| 「同步可选外挂」 | E4 服务端 snooze 队列会让提醒依赖服务端；E3 自动同步让可选变成默认写盘者 |
| 「不引依赖，锁用内置」 | 跨平台/跨进程锁自写更危险；「唯一写者」只是文档不是机制 |
| 非目标把「WebDAV 删除传播」留作待决策 | 数据安全级决策不应留到 SDS |

## 范围与顺序建议

- 只做三件：**E6（可信 CI/类型）→ E2（数据可靠性）→ E1-min（认证，无 loopback 回退）**。
- 理由：没有可信 CI，E2 的并发/崩溃验收不可信；数据丢失不可逆，优先于暴露面；
  E1 砍到「必配 token + fail-closed + OPTIONS 豁免」只需 1–2 天，不必先做。
- E3 降级为**只读统一状态面板**（聚合现有通道 API），不做新调度器。
- 砍掉：墓碑、迁移框架、`/api/auth/*`、WebDAV debounce、历史 50 条（先 20 条只读）。

## 可测试验收（摘要）

1. 不配 token：`/api/*` → 401，`/health` → 200；loopback 也 401。
2. 带 Authorization 的 OPTIONS → 204 + 正确 ACAO；无 token GET → 401。
3. Nginx + `trust proxy=1` 下伪造 `X-Forwarded-For: 127.0.0.1` → 仍 401。
4. Electron `file://`（Origin null）注入 token 后可读写；无 token 显示输入框。
5. 同一 item 的 `title` 与 `due` 并发修改 → 两字段都保留。
6. 50 请求 + 同时一次 CalDAV pull → 条目数正确、无解析错误。
7. tmp 写完、rename 前 kill -9 → 重启后旧版本可解析，tmp 被清理。
8. 恢复 3 天前备份 → 覆盖前 diff 预览；恢复后首次同步不全量冲突；旧提醒不重发。
9. 1 分钟间隔 + 连点「立即同步」5 次 → 远端只收到一轮请求。
10. 自动同步遇 412 → 转「需人工」，本地不覆盖，冲突数 1。
11. 墓碑（若做）：同 uid 两实例，删一个只少一个 href。
12. 未知字段/块往返逐字节保留。

## 必须回答的问题（推荐默认）

1. 未配 token 允许访问？→ **否，只 `/health`**。
2. 支持反代？→ **支持，但只认显式 `TRUST_PROXY_HOPS`，默认 0**。
3. 自动同步遇冲突？→ **暂停转人工，永不自动 force/merge**。
4. 墓碑？→ **v0.3 不做**；做时键为 href。
5. 迁移框架？→ **不要**，只做未知字段往返保留。
6. 恢复后同步状态？→ **重置 etag + 全量重扫**。
7. 锁边界？→ **单进程、仅临界区、网络 IO 锁外；多实例文档不支持**。
8. 工期基线？→ **E2 + E1-min ≥ 10 人日**，E3 另算。

## 对流程的批评

- **决策无限下推**：计划有 10 条待决策就进 SDS，SDS 作者替 owner 做选择，
  实施会话再替 SDS 做选择，错误在三层放大且无人认领。
- 两个「互不通气」的评审都基于同一份初稿、都不读代码，会收敛到同样盲点。
- 新会话实施丢失隐含假设：SDS 没写「同步任务也在锁内」，实施 agent 就不会加。

改进：SDS 前先出 **ADR 式决策记录（8 条、带默认值与失效条件）并签字**；
SDS 按 Epic 拆三份、每份 ≤5 页，必须含「不做什么」「如何证伪」；
每个实施 PR 附一个**能失败的测试**；评审 agent 至少允许读 `workspace.ts` 与 `index.ts`。

## 结论

**必须先补决策。** 门槛：

1. 8 条决策落纸并签字；
2. E2 单独立 SDS，含真实断电/崩溃测试方法；
3. 认证 fail-closed，删除 loopback 回退；
4. 墓碑与迁移框架移出 v0.3；
5. 工期按 15–20 人日重估。
