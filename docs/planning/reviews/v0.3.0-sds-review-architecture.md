# v0.3.0 SDS 架构 / 安全 / 数据完整性评审

- 评审对象：`docs/planning/v0.3.0-sds.md`（Draft for independent review，2026-11-02）
- 对照基线：`docs/planning/v0.3-plan.md`（v1.0）、`docs/planning/reviews/decision-log.md`（D1–D27）、`docs/DEV_RULES.md`
- 评审人：独立评审（未参与 SDS 编写，未修改代码或 SDS）
- 方法：文档逐节对照 + 现有代码静态核对；**未执行测试，未访问真实 NAS / CalDAV / WebDAV**
- 结论：**不通过**

## 0. 结论摘要

SDS 的方向是对的：数据先于认证、单一写入口、prepare/commit、round-trip、恢复 marker 都是正确投资。但当前文本存在 **2 个安全洞、2 个并发/恢复数据完整性洞、1 个可用性洞**，且其中 3 个与已定决策或 v1.0 验收直接冲突。按现文实现会出现「验收 #3 失败」「空 token 可认证」「merge 重入锁死」「恢复期间写入被静默覆盖」「读失败进程崩溃」中的至少一个，因此不能作为实现契约放行。

## 1. 阻断问题（5）

### B1 [P0 / 安全] createApp 把 static+SPA fallback 放在 auth 之前，`/API/...` 绕过 401 验收

**位置**：SDS §3.2 步骤 4–5（static + SPA fallback 在 `app.use("/api", auth)` 之前），与 plan §4.2 最终顺序（static → `/api` auth → json → 路由 → SPA fallback，步骤 3/4/5/6/7）及验收 #3 冲突；现有实现见 `apps/server/src/index.ts:64-74`。

**具体失败场景**：实现者按 SDS 顺序复用现有 SPA 正则
`app.get(/^\/(?!api\/|health$|assets\/|sw\.js$|workbox-|manifest\.json$).*/)`
（**大小写敏感**）。无 token 请求 `GET /API/workspace/items`：`express.static` 未命中 → SPA fallback 的负向前瞻只匹配小写 `api/`，因此命中并返回 `index.html` **200**，而不是 401；`/Api/...` 同理。SDS §3.2 末尾却断言「`/API/...` 由 Express 大小写不敏感匹配，仍经过 auth」，与自身中间件顺序矛盾。此外，若 `staticDir` 下恰好存在 `api/...` 文件，static 会在 auth 之前直接公开它，绕过认证。

**最小修复**：严格按 plan §4.2 顺序：cors → `/health` → static（显式跳过 `/api`，或放在 API 路由之后）→ `app.use("/api", auth)` → json → 全部 API 路由 → SPA fallback → 404 JSON；SPA 排除条件改为 `/^\/api(\/|$)/i`；测试覆盖 `/API`、`/Api`、`/api//`、`%61pi` 与 static 下 `api/x`。

### B2 [P0 / 安全] token 文件为空/损坏时可能得到空 token，`fail-closed` 实际不成立

**位置**：SDS §3.1（env 非空 → 文件 → 生成；写文件 0600；比较 `sha256(token)` 与 `sha256(candidate)`）；当前无认证实现。

**具体失败场景**：token 文件可能因非原子写入中断、手工 `touch`、容器卷恢复为空文件或只含换行。若 `resolveApiToken()` 对文件内容只做 `readFileSync(...).trim()` 后直接返回，则 token 为 `""`；认证中间件用 `sha256("")` 与 `sha256("")` 做 `timingSafeEqual`，长度相同、结果相等，攻击者发送 `Authorization: Bearer `（或空 Bearer 值）即通过。SDS 只规定 env 必须「非空」，未规定文件内容必须非空/格式合法；也未规定对已存在文件执行 `chmod 0600`（`writeFile(..., {mode:0o600})` 不会修改已存在文件的权限）。空 token 还使「token 256-bit，熵足够」的 D17 前提失效。

**最小修复**：读取后 `trim()`，要求 `/^[0-9a-f]{64}$/`（或至少 32 字节）否则视为损坏：重新生成并原子写 0600，或直接 throw 拒绝启动（二选一写进 SDS）；`createApp` 对 `token.length === 0` 立即 throw；比较前显式拒绝空 candidate；token 文件用 `atomicWriteFile` + `fchmod`；补「空文件/仅换行/截断/0644」测试。

### B3 [P0 / 数据完整性] WebDAV merge 的「锁内复核 + mutateWorkspace」嵌套同一把锁，且 baseHash 与合并读取不是同一快照

**位置**：SDS §2.7 WebDAV merge 步骤 1–4；D12「禁止重入、仅读-改-写临界区」；现有直写见 `apps/server/src/routes/webdav.ts:466-525`（PUT 成功后 `fs.writeFileSync` 于 505 行）。

**具体失败场景**：
1. 步骤 4 写的是「锁内复核 baseHash …… 写本地（`mutateWorkspace` 内写 merged text）」。若外层已 `withWorkspaceLock`，再调 `mutateWorkspace` 会再次取锁：`AsyncLocalStorage` 重入检测直接 throw（或 10s 后 `LockTimeoutError` 503）。实现者为绕开，很可能退回 `writeFileSync`，重新引入无锁写与「PUT 成功后本地写」竞态。
2. `baseHash = sha256(localText)` 在步骤 1 记录，合并文本却在步骤 2 基于「最新本地」**第二次读取**重算。若本地在两次读取之间被改：merged text 已包含新改动，PUT 成功，但步骤 4 用旧 baseHash 复核必然不匹配 → 返回 409「请重新合并」，实际没有新的并发改动；用户重试仍可能因同一窗口反复 409。
3. `mutateWorkspace` 的契约是「模型 → `serializeWorkspace`」，无法写入远端合并后的原始文本；未知块/frontmatter 的排序与格式会被重写，下一次 merge 又看到文本差异。

**最小修复**：把 merge 提交定义成**一次** `mutateWorkspace((ws) => { if (sha256(ws.raw) !== baseHash) throw MergeConflict; /* 用 ws.raw 同一快照计算并整体替换 */ })`；`baseHash` 必须取自参与合并的那一次 `ws.raw`，不要在锁外另读一次；若确需「锁内调内部写」，提供仅内部可用的 `mutateWorkspaceLocked` 并明确 ALS 深度语义，禁止公开嵌套。补「baseHash 与 merge 读取之间改本地」「PUT 期间改本地」「锁内重入」三类测试。

### B4 [P1 / 数据完整性] restore 的 maintenance 只停调度器；state 重置在锁外；手动同步与普通写入不设防

**位置**：SDS §4.3 步骤 3–7（`maintenance=true` 仅「调度器 tick 直接 return」；步骤 5 锁内覆盖，步骤 6 状态重置在锁外）；§10「用户点重新合并/拉取/推送后清除 suspend」；D11。

**具体失败场景**：
1. 恢复等待 `inFlightSync` 的 10s 窗口内，普通 `POST /api/workspace/items` 不受 maintenance 限制，仍可成功；步骤 5 用 pinned 内容覆盖后，该用户刚创建的任务只在 `pre-restore` 备份里，UI 没有任何提示。
2. 步骤 5 释放锁后、步骤 6 rename `.caldav-sync-state.json` 时，手动 `/api/caldav/sync`（或已排队 sync）可启动并 `writeSyncState`；rename 与写竞争，可能把**新** state 重命名进 `.pre-restore-<ts>`，或旧 etag 重新出现。下一次 pull 以旧 etag 判断「远端没变/变了」，覆盖刚恢复的本地内容。
3. `sync-suspended.json` 只约束「自动同步」（§4.3 步骤 7、§10），手动同步入口是否检查未定义；`epoch` 在「取到远端后 / 进入 mutate 后 / 写 state 前」哪几个点校验也未定义。若只包网络阶段，commit 与 state 写仍可在恢复后落地。
4. 步骤 5 没有规定 `pre-restore` 备份失败时中止；按 §2.2「备份失败仅告警」的惯例，可能在无回滚副本的情况下覆盖事实源。

**最小修复**：maintenance 期间对所有 mutating `/api`（除 restore/status/health）返回 503；`epoch` 在 sync 的每个 commit 与每次 state 写前校验；restore 在同一把锁内完成「覆盖 + 状态重置」，或状态写也带 epoch；`sync-suspended` 在 sync service 入口硬拦（含手动）；`pre-restore` 备份失败必须 abort 并保留 marker；恢复前对 pinned 内容做 `parseWorkspace` + 图校验。补「恢复中 POST」「恢复中手动 sync」「state rename 与 writeSyncState 竞争」「备份失败」测试。

### B5 [P1 / 可用性 + 数据] readWorkspace 仍按 existsSync 判 ENOENT；throw 后的调用方与错误中间件未定义

**位置**：SDS §2.1（ENOENT 空、其他 fs 错误 throw、API 500 JSON）、§2.2、§3.2；现有 `apps/server/src/workspace.ts:456-472`；未捕获调用点 `apps/server/src/notifications/scheduler.ts:191,278`、`apps/server/src/caldav-sync.ts:987`、`apps/server/src/routes/workspace.ts` 各同步 handler。

**具体失败场景**：
1. 文件/父目录 `EACCES`、`EISDIR`、`EIO` 时，`fs.existsSync()` 通常返回 **false**（不抛错）。若实现保留现有 `existsSync` 预判，会被当成「首次启动」返回空集合 200；紧接着一次创建请求经 `mutateWorkspace` 重读（新实现仍可能用同一判定）→ 写回只有新条目的文件，事实源被清空。这正是 §2.1 想防的失败模式，但文本没有要求移除 `existsSync`。
2. `readWorkspace` 改为 throw 后，scheduler 的 async tick / `getCalDAVSyncStatus` 没有捕获，Node 22 默认会把未处理 rejection 变成进程退出；Docker `restart: unless-stopped` 形成崩溃循环，用户恰好无法打开备份/恢复页修复。同步路由中的 sync throw 在 Express 4 下进入默认错误处理器，返回 HTML（非 production 还带 stack/绝对路径），不是约定的 500 JSON。
3. §2.1 规则 3「解析后 0 条有效条目」未定义「有效」：现有 `parseWorkspace` 会把缺少 id 的坏块也 push 进 `items` 并带 `errors`，按 `items.length` 判断会漏掉「全坏」；按 `errors.length` 判断则需把 `validateItem` 纳入解析路径。

**最小修复**：读路径改为 `try { readFileSync } catch (e) { if (e.code === "ENOENT") return empty; throw new WorkspaceReadError(...) }`，不使用 `existsSync` 做存在性判定；在 `createApp` 末尾加统一 error middleware（`WorkspaceReadError`/`LockTimeoutError`/`WorkspaceValidationError` → JSON，且不返回绝对路径）；每个后台循环/路由捕获并记录一次；规则 3 明确「有效 = `errors` 为空」，并给出全坏样例。补 chmod 000/EISDIR、scheduler tick、500 JSON content-type、读失败后不写测试。

## 2. 非阻断问题（10）

1. **§2.5 未知块标记不可逆**：序列化在 notes 之后写 `<!-- unknown -->`，但解析器只识别 `<!-- notes -->`（`apps/server/src/workspace.ts:196-205` 之后全部归 notes），再解析时未知块被吞进 notes，`serialize→parse→serialize` 不稳定，S5 的幂等断言会失败。需定义 `<!-- unknown -->` 的解析段，或把未知块放在 notes 之前。
2. **§2.5 只规定「字段值」换行转义，title 不是字段**：`serializeWorkspace` 把标题写成 `## ${item.title}`（`workspace.ts:414`），title 含 `\n` 会直接注入新条目/破坏块结构；SDS 却明确要求测试 title 含换行。另 `\n` 的解析无法区分「字面反斜杠+n」与转义换行，需定义反斜杠转义。
3. **frontmatter 表示有损且 schema 会被降级**：`Record<string,string>` 无法保留 YAML 列表、嵌套、多行、注释与空行；`serializeWorkspace` 固定写 `schema: workbench/v1`（`workspace.ts:401`）。v0.4 的 `schema: workbench/v2` 文件被 v0.3 打开后会被静默改写为 v1，违反 D6「只做往返保留、不迁移」的谨慎原则。需保留原始 frontmatter 文本或至少对未知 `schema` 值拒绝写入。
4. **§2.6 图校验按整文件执行，远程坏数据会永久卡死同步**：CalDAV pull / WebDAV pull 的 `mutateWorkspace` 只要遇到一条 `end <= start`、重复 id 或孤儿 parent 的远端对象就整体 throw，该对象下一轮仍会被拉回，同步永远无法前进。应对远端来源做逐条隔离（跳过并 `recordSyncEvent`），仅结构性损坏才 abort。
5. **§2.4 原子写 tmp 名固定为 `${filePath}.tmp.${pid}`**：同一进程内对同一 state/config 文件的并发写（自动同步 + 手动同步都写 `.caldav-sync-state.json`；设置页 PUT + 启动读改写 config）会共用 tmp，出现 rename ENOENT 或内容混合。加随机后缀或按路径互斥；同时 `pre-restore` 备份失败必须 fatal，不能沿用「失败仅告警」。
6. **CalDAV push 的 ETag 续期不可靠，且措辞与 plan 冲突**：成功分支 `normalizeEtag(res.headers.get("etag")) ?? etag`（`caldav-sync.ts` 约 935/940 行）在服务器不回 ETag 时保留旧值，下一轮 If-Match 必 412，形成永久冲突。PUT 后应重新 GET 或把「未知 etag」显式落为无 If-Match。另 §2.7 写「变化 → 标记 pending，不覆盖远端」，但 PUT 已发出，**不可能不覆盖远端**；plan A-C3 已改为「下一轮 If-Match 收敛」，SDS 必须对齐，否则实现者会尝试不可实现的回滚。
7. **restore 的 `file` 路径安全与哈希时序未定义**：§4.2 的 basename/realpath 校验只写在 preview/export；§4.3 只说「校验 file/sha」。必须明确：basename、realpath 在 `.workspace-backups` 内、优先读 `.pinned/<sha256>.md`、对**同一 Buffer** 计算 sha 后写入（避免校验与读取之间被替换）；`.pinned` 24h 清理可能删掉预览目标，需定义 404/409 与「重新预览」路径。
8. **Electron token 经 `additionalArguments` 暴露在 renderer argv**：`--dsh-token=<token>` 出现在渲染进程命令行，Linux `/proc/<pid>/cmdline`、macOS `ps` 对其他本地用户可读，绕过了 `userData/api-token.txt` 的 0600 保护。改用主进程 `webRequest.onBeforeSendHeaders` 注入 Authorization，或 IPC 到 preload；另 SDS §3.6 只传 `HOST` env，但当前 `index.ts:97` 是 `app.listen(PORT)`（绑定 0.0.0.0），必须显式 `listen(port, "127.0.0.1")`。
9. **Docker / NAS 取 token 与只读 `/data` 自相矛盾**：`docker-entrypoint.sh:8`
 执行 `chown -R app:app /data`，token 由 app 用户以 0600 创建，宿主机普通用户（uid 1000）执行 `cat data/api-token.txt` 会 EACCES；文档应改为 `docker exec caldav-desktop cat /data/api-token.txt`（exec 默认 root）或 0640 + 明确组。另 `/data` 只读时 `verifyStorageSafety` 默认 `process.exit(1)`（§2.4），根本到不了 §3.1「token 写失败仍启动」的分支；需统一为「存储自检失败即拒绝启动」，并删除/改写 token 降级承诺。
10. **v1.0 验收与 D19 有未落地项**：plan §4.4 / 验收 #17 的「全局连接状态横幅 + mutation 失败 toast + 错误页」在 SDS §7 完全缺失；令牌页的「升级须知 / 导出备份」也缺失。D19 把 md-bridge/kanban 读接口决定权交给 SDS，SDS §2.2 只下线写、未决定读；`apps/server/src/routes/md-bridge.ts:88,143,527` 仍接受任意 `filePath`，若保留读接口，v0.2.5 无认证期间就是 LAN 任意文件读取。另 `Calendar.tsx:542` 走的是 `api/md-bridge.ts:169` 的第二个 `exportIcsDownloadUrl`，§3.5 只点名 `api/workspace.ts`，会漏改。

## 4. 测试缺口（需补进 §8 / CI）

1. **Token 边界**：空文件、仅换行、截断 hex、0644 已存在文件、`API_TOKEN=""` + 不可写文件、`Authorization: Bearer ` 空值；断言空/损坏 token 不能认证，且启动日志不出现 token。
2. **路径与中间件**：`/API`、`/Api`、`/api//`、`/api%2F...`、`%61pi`、staticDir 下 `api/x`、未知 `/api/foo` 的 404 JSON、SPA 非 api 路由 200；OPTIONS 在「不允许的 Origin」下不应被当成认证成功。
3. **读失败**：chmod 000（覆盖 `existsSync` 返回 false 的分支）、EISDIR、mock `readFileSync` throw；断言 500 JSON、文件字节不变、scheduler tick 不崩、Docker 不重启循环。
4. **锁与并发**：merge 在 `withWorkspaceLock` 内调 `mutateWorkspace` 的行为（应 throw 而非死锁）；自动+手动 sync 同时写 state；config PUT 与启动写并发；50 并发 mutate 下备份文件不互相覆盖。
5. **restore 全阶段崩溃**：写 marker 后、等待 inFlight 中、覆盖后/state 重置前、caldav state rename 后/reminder state 前、suspend 写入后/清 marker 前；每阶段重启后断言「不自动同步、可重试、文件可解析」。
6. **restore 并发**：恢复中 POST 创建/编辑；恢复中手动 `/api/caldav/sync`；inFlight 超时 503 后重试；`pre-restore` 写失败；pinned 内容不可解析；`file=../workspace.md`、绝对路径、sha 与文件内容不匹配、预览后 24h 过期。
7. **merge 分支**：baseHash 采样与合并读取之间本地被改；PUT 期间本地被改；PUT 412；远端 ETag 缺失；未知块/frontmatter 在 merge 后仍保留。
8. **round-trip**：`<!-- unknown -->` 再解析、title 含换行、description 含字面 `\n`、frontmatter 列表/嵌套/注释、schema v2 输入、幂等两次序列化字节相等（或结构相等）。
