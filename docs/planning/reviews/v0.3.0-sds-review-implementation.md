# v0.3.0 SDS 独立评审（实现 / 测试 / 发布）

- 评审对象：`docs/planning/v0.3.0-sds.md`（611 行）
- 对照：`docs/planning/v0.3-plan.md`、`docs/planning/reviews/decision-log.md`（D1–D27）、`docs/DEV_RULES.md`
- 代码基线：`apps/server/src/{index,workspace,caldav-sync}.ts`、`routes/{workspace,webdav}.ts`、`notifications/scheduler.ts`、`apps/desktop/{main,preload}.ts`、`apps/desktop/electron-builder.config.json`、`apps/renderer/src/api/base.ts`、`modules/index.ts`、`components/settings/ConfigSettings.tsx`、`i18n/locales/{zh-CN,en-US}.ts`
- 评审立场：独立评审，不修改代码与 SDS；唯一写入是本文件。

## 结论

**Verdict：不通过。**

SDS 的总体方向和边界（单用户 Bearer、进程内锁、原子写、只读同步中心、恢复后暂停同步）是清楚的，但数据层、恢复状态机、Electron 打包、Docker 只读/token 取用、写路由错误契约这五处存在“按文档实现会坏”的问题：要么必须自行发明接口，要么直接违反 v1.0 验收。建议按下列 5 条修完 SDS 后再进入 P1。

## Blocking issues（5）

### B1【高】图校验与“坏条目不阻塞”互相矛盾，一次脏数据会永久锁死所有写入

- 位置：SDS §2.2 步骤 4（L100）、§2.5 规则 4（L172）、§2.6（L186–193）；对照 §2.1 规则 4（L80）。
- 失败场景：`workspace.md` 里有一条历史遗留的缺 `id`、孤儿 `parent` 或 `end <= start` 的条目。`readWorkspace` 按 §2.1 规则 4 保留它（`ParsedItem.errors`），但任何 `mutateWorkspace`（包括新建一条**无关**条目）都会在步骤 4 对**全部** items 调 `validateWorkspaceGraph`，id 唯一/`end > start` 校验失败 → `WorkspaceValidationError` → 400。结果是用户永远无法通过 API 修复这条脏数据，只能手改文件；这与“坏条目不阻塞其他条目”的承诺直接冲突。
- 加重项：§2.1 规则 3 的“解析后 0 条有效条目”没有定义“有效”。实现者若把带 `errors` 的条目算无效，一个只有坏条目的文件会在每次读取时 500，且没有 UI 修复路径。
- 最小修复：在 SDS 中定义 `validItem = !item.rawBlock && (!item.errors || item.errors.length === 0)`；`mutateWorkspace` 只校验“被 `fn` 修改且 `!rawBlock`”的条目，或允许 `opts.validate=false`；把规则 3 改为“0 条可解析条目（既无 id 也无任何已知字段）”，并在错误里给出文件路径与手动修复提示。

### B2【高】恢复状态机依赖三个不存在的接口，in-flight 同步可在恢复后回写旧数据

- 位置：SDS §4.3 步骤 3–5（L388–399）、§2.7；代码 `apps/server/src/caldav-sync.ts:635`（私有 `inFlight`）、`:1054`（`stopCalDAVAutoSync()` 只 `clearInterval`）、`:980`（`getCalDAVSyncStatus()` 内部还会 `readWorkspace()`）；`apps/server/src/notifications/scheduler.ts:191/278`（无 maintenance 闸门）。
- 失败场景：恢复时 CalDAV pull 正在 `doSync` 中（已读旧 items，尚未写）。SDS 要求“等 `inFlightSync` / `epoch` 丢弃”，但现有模块没有导出的等待、取消或 epoch 接口；`inFlight` 是模块私有变量，`stopCalDAVAutoSync()` 不会等它。实现只能猜。若恢复不等待，pull 会在恢复覆盖之后把旧 items 写回，用户刚恢复的数据被静默覆盖；若实现者自己加全局变量，又拿不到 `inFlight`。调度器同样没有 maintenance 标志，恢复窗口内仍会读 workspace、写提醒状态。
- 最小修复：在 `caldav-sync.ts` 导出 `waitForInFlightSync(timeoutMs): Promise<boolean>`、`invalidateSyncEpoch(): number`、`currentSyncEpoch(): number`；每次 sync 开始时记录 epoch，所有 commit 写回前比对，不一致则丢弃并记事件。`scheduler.ts` 导出 `setMaintenance(boolean)`，或在 `createApp` 注入 `isMaintenance()`。SDS 需写明这些签名、调用顺序，以及 10s 超时后“保留 marker、返回 503”的具体路径。

### B3【高】Electron 打包链路按 SDS 改完仍启动不了：server 不在包内，base URL 被 .env 覆盖

- 位置：SDS §3.6（L307–323）；代码 `apps/desktop/main.ts:13–15`（fork `../server/dist/index.js`，env 只加 `PORT: "3001"`）、`apps/desktop/electron-builder.config.json`（`files` 只有 `dist/**/*` 与 desktop 的 `node_modules`，没有 `apps/server/dist` 和 express/tsdav/multer 等生产依赖）、`apps/renderer/src/api/base.ts:27–38`（注入值为空则回落 `VITE_API_URL`）、`apps/renderer/.env`（已提交 `VITE_API_URL=http://localhost:3001`）。
- 失败场景 A：打包后 `resources/app.asar/server/dist/index.js` 不存在，`fork` 立即退出，主进程轮询 `/health` 永远失败，窗口不加载；即使手工把 server dist 拷进去，desktop 的 `node_modules` 没有 express 等依赖，会 `ERR_MODULE_NOT_FOUND`。
- 失败场景 B：preload 按 SDS 注入 `__API_BASE_URL__ = ""`，但 `base.ts` 用 `injected.trim()` 判空，空字符串被忽略，renderer 继续使用构建时烘进的 `http://localhost:3001`；随机端口下所有 API 打到错误端口（甚至打到本机 3001 上的其他服务），AuthGate/401 逻辑也救不回来。
- 最小修复：electron-builder 增加 `extraResources`（server dist + 生产 node_modules，或用 esbuild 打单文件），`main.ts` 用 `process.resourcesPath` 解析 server 路径；Electron 的 renderer 构建显式 `VITE_API_URL=`，并改 `base.ts` 为“注入值为字符串时即使空也视为权威”，preload 注入实际的 `http://127.0.0.1:${port}`。P6 的验收必须是“打包后安装并启动”，不能只跑 dev。

### B4【高】`/data` 只读与 token 取用：SDS 会 exit(1)，0600 又让宿主机 `cat` 失败

- 位置：SDS §2.4（L147–151）默认 `process.exit(1)`；§3.1（L228–240）0600；§3.7（L325–332）“`cat data/api-token.txt`”；对照计划 §6 验收 14（`docs/planning/v0.3-plan.md:358`）和 §4.1（`:230`、`:282`）“只读 `/data` 启动继续、token 一次性打印”；`docker-entrypoint.sh` 对 `/data` 执行 `chown -R app:app`（容器内 uid 100）。
- 失败场景 A：把 `./data` 挂成只读，`verifyStorageSafety` 写测试文件失败，进程在 `listen` 前退出；验收 14 要求的“启动继续 + token 打印”根本不会发生，用户既没有 UI 也没有 token。
- 失败场景 B：正常 Docker 下 token 文件 `0600` 属 uid 100；宿主机用户（常见 uid 1000）按文档执行 `cat data/api-token.txt` 得到 `EACCES`；群晖 File Station/SMB 以普通用户访问同样可能被 ACL 拒绝。文档给出的取 token 主路径不可用。
- 最小修复：明确启动顺序为“先 `resolveApiToken`（写失败打印 token），再 `verifyStorageSafety`”；只读/写测试失败默认降级为 WARN 继续（读多写少的本地优先应用不应因 `/data` 只读拒绝启动），或自动视为 `ALLOW_UNSAFE_FS=1`；取 token 文档改为 `docker compose exec caldav-desktop cat /data/api-token.txt`（exec 默认 root）并删除宿主机 `cat` 承诺，或把 token 文件设为 `0644` 并在 D1 记录这一单用户 LAN 权衡。

### B5【高】写路由迁移缺错误契约，404/409/400 会变成 500 或挂起

- 位置：SDS §2.2 迁移表（L105–115）、§2.6（L186–193）、§6 错误（L462–466）；代码 `apps/server/src/routes/workspace.ts:298/398/446/651/813` 目前都在 handler 内先 `readWorkspace()`，再按 404/409/400 直接 `res.status(...)`。
- 失败场景：`POST /api/workspace/items` 重复 id 现在返回 409；迁到 `mutateWorkspace` 后，判断只能放进 `fn`。若在 `fn` 内 `throw new Error(...)`，外层 `catch` 会统一变成 500（现有测试期望 409）；若 handler 直接 `await mutateWorkspace` 而没有 try/catch，Express 4.19 不会转发 async rejection，请求会挂到客户端超时。SDS 只定义了 `WorkspaceValidationError` 和 `LockTimeoutError`，没有 404/409 的领域错误，也没有全局错误中间件，实现者必须发明。
- 最小修复：定义 `WorkspaceHttpError(status, code, message)`（或让 `mutateWorkspace` 返回 `{ ok:false, code }` 的显式结果），在 `createApp` 末尾加 4 参错误中间件映射 400/404/409/503，并要求所有 async handler 用 `asyncHandler` 包装；在 §6 按接口列出错误码（尤其 ICS import 的 409/400、PUT 的 404）。

## Non-blocking issues（10，每条一行）

1. §3.2 步骤 4 把 SPA fallback 放在 auth 之前，而现有 `apps/server/src/index.ts:68` 的正则只排除小写 `api/`；`/API/workspace/items` 会先命中 index.html 返回 200，验收 3 失败——fallback 必须用大小写不敏感排除 `/api`，或在 static 前先挂 `/api` 鉴权。
2. §9 的 P6 单独落地时 renderer 还没接 token、base 仍固定 3001（P7 才改）；P6 之后 Electron 全 401/打错端口，bisect 不可用——把 P6 与 P7 合并，或 P6 内先做 `base.ts` 空值修复 + 最小 Authorization。
3. P3“下线 legacy 写”（D19）没有列出保留哪些读接口，也没列要删/改的测试（`apps/server/src/__tests__/e2e-bridge.test.ts`、`kanban-id.test.ts`、`ui-smoke.test.tsx` 都 mock 了 `/api/md-bridge`、`/api/kanban`）——P3 应先给出端点与测试清单。
4. §4.2 备份列表的 `itemCount` 若复用 `readWorkspace`，一个“全部条目坏”的旧备份会抛 `WorkspaceReadError`，整个列表 500，恰好在最需要恢复时看不到备份——列表/预览必须用容错 parse，单文件失败标 `itemCount:null`。
5. §4.2/4.3 restore 需要 `sha256`，但列表不返回 sha，只有 preview 返回；预览后超过 24h `.pinned` 被清理，restore 读 pinned 的错误码未定义——明确 `RESTORE_SNAPSHOT_EXPIRED`（409），或列表返回已 pin 的 sha。
6. §5 同步中心“查看冲突”没有数据源：overview 的 caldav 只有 `lastError`，webdav 只有 409 瞬时响应，没有 `conflicts[]`；按钮点击后展示什么未定义——要么 overview 增加最近冲突 ring，要么去掉按钮。
7. §5 写的 `caldavSyncStatus()` 对应现有 `getCalDAVSyncStatus()`（`apps/server/src/caldav-sync.ts:980`），后者内部 `readWorkspace()` 会抛错且没有 `lastError`；overview 必须 try/catch 并填 `lastError`，否则数据文件坏时同步中心整页 500。
8. §4.3 恢复没有并发/幂等闸门：两个 restore 同时通过步骤 1–3，marker 互相覆盖，两个都执行覆盖与状态重置——加进程内 restore mutex，第二个返回 409“恢复进行中”，并在步骤 5 校验 marker epoch 未变。
9. §8 的 S3/S4 用 `WORKSPACE_CRASH_AFTER_TMP=1`/`process.exit(1)`，若在 vitest 进程内执行会直接杀掉 worker——必须写明用 `child_process.spawn` 起独立进程并断言退出码/日志，否则测试不可实现或必然 flaky。
10. §8.1 把 Docker 用例 S13 列在服务端 vitest，但 CI 无 Docker 时跑不了——改为 `scripts/docker-smoke.sh` + 手工门禁，或单独 `docker build` job；9p/SMB 的自检误判也只有手工覆盖。

## Test gaps（现有 S1–S13 / F1–F7 之外必须补）

1. **脏数据 + 无关写入**：文件中有一条缺 id 的坏条目，再 POST 一条新条目，断言 200、坏块原样保留（直接覆盖 B1）。
2. **恢复竞态**：用可控 deferred 卡住 CalDAV pull 的写回和 WebDAV merge 的 PUT，执行 restore，断言旧数据没有在恢复后落盘；再测 restore 与 restore 并发。
3. **恢复中断矩阵**：覆盖前 / 覆盖后状态重置前 / 清 marker 后写 suspend 前 / pinned 已被清理 / 连续两次恢复；每种都断言重启后 `restorePending` 与自动同步暂停。
4. **备份容错**：备份目录含损坏文件、空文件、旧 schema、无 frontmatter、重复 id 的文件，`GET /backups` 仍 200，坏文件有标记；预览 diff 覆盖 title 与 due 两类 changed。
5. **token 可取得性**：Windows 上 `0o600` 断言无意义，需断言生成成功而非权限位；Docker 内 uid 100 与宿主机 uid 1000 的读权限；`API_TOKEN_FILE` 指向不存在/只读路径。
6. **认证绕过**：`/API/...`、`/api//...`、`/api%2F...`、`//api/...`、无 token 的 `OPTIONS /api/...`、`Origin: null`、不在白名单的 Origin 401 是否带 ACAO。
7. **createApp 边界**：`staticDir` 不存在、`index.html` 不存在、`/api` 路径与 SPA 路由同名、`trust proxy` 非法值。
8. **Electron 打包冒烟**：安装包启动后 asar 内 server 路径、生产依赖、随机端口、`VITE_API_URL` 为空、preload argv 缺失/解析失败时 AuthGate 回退。
9. **前端 401 风暴**：9 个 client 同时 401 只显示一次 gate；输入 token 后 reload 保留；清除 token 后 Electron 注入 token 的优先级；`dsh-auth-required` 重复派发不叠加。
10. **同步中心容错**：`.webdav-state.json`/`.caldav-sync-state.json` 损坏、`readWorkspace` 抛错、未配置/失败/冲突时 overview 仍 200 且有 `lastError`。
11. **WebDAV merge 竞态**：下载后本地被另一请求修改，409 且本地未被写；412 时本地状态不变；“只允许重新合并”的 UI 不出现覆盖按钮。
12. **提醒恢复**：sent 交集按 `id|remind` 精确匹配、`remind` 为空、恢复后第一次 tick 不重复推送。

## Assumptions

- 评审基于当前 611 行 SDS 与 `v0.3-plan.md`、`decision-log.md` D1–D27；文中代码行号是当前基线，后续重构以接口为准。
- D1 的 `0600` 是硬约束；Docker entrypoint 的 `chown -R app:app /data` 与 uid 100 是发布形态。
- Express 4.19 默认大小写不敏感路由；async handler 的 rejected promise 不会被自动转发（4.x 行为）。
- Electron 28 + electron-builder 24；electron-builder 的 `files` 以 `apps/desktop` 为根。
- “有效条目”按“可解析出 id 或至少一个已知字段”理解；若作者另有定义，B1 的冲突仍然成立。
- CI 可 spawn 子进程，但不假定有 Docker；9p/SMB 与 NAS File Station 只做手工验证。
