## 结论

**有条件通过。**

v0.2 确实逐条吸收了前两轮 10 个阻断项的大部分契约，方向正确；但仍有 5 个会影响“可实施 / 可发布 / 可测试”的问题，其中恢复停机死锁、提醒调度竞态、P2→P3 构建断裂属于必须先修的实现级阻断，不是文档措辞问题。修掉下列 5 项后可进入 P1。

## 阻断项（5）

### BK1 [高] P5/P6 与 P7/P8 的拆分仍会产生坏中间版本

- 证据：§9 P5 只做“auth.ts + token 校验 + createApp auth/CORS/order + 服务端测试”，P6 才做“前端 token/base/AuthGate”（`docs/planning/v0.3.0-sds.md:735-737`）。P5 合入后所有 `/api` 立即 401，但浏览器端还没有 token 输入页和 Authorization 注入，P5 单独不可用。同理 P7 在恢复时写入 `sync-suspended.json` 并硬拦 CalDAV/WebDAV（§4.3），而清除 suspend 的 `POST /api/sync/resume` 和 UI 在 P8（§5），P7 单独合入后同步永久停摆，只能手工删文件。
- 为何是阻断：P6 已为“Electron 先落地但前端仍 401/3001”合并旧 P7（`:739`），说明项目把“每个 PR 可回滚/可发布”作为门禁；P5/P6、P7/P8 是同一类坏 bisect，且 P8 只依赖 P5（`:738`），当前顺序并非唯一可行顺序。
- 要求修复：把 P5 扩为“服务端 auth + 最小 token 输入/AuthGate/请求注入”，或 P5+P6 合并；把 P7 扩为“恢复 + 最小 resume 入口”，或 P7+P8 合并 / 调换 P8 在 P7 之前。明确 v0.2.5 tag 在 P5 之前，v0.3.0 只在 P9 打 tag，且每个 PR 的验收包含“升级后 UI 可登录、恢复后可恢复同步”。

### BK2 [高] 恢复失败路径没有出口：maintenance 会把“重新预览”也锁死

- 证据：§4.3 `:554-555` 规定 maintenance 覆盖所有 mutating `/api`，仅放行 restore/status/health/overview；而“重新预览”是 `POST /api/workspace/backups/preview`（§4.2 `:514`、§6 `:616`），会被 503。`:561` 规定启动时发现 marker 就 `maintenance=true`；`:564` 又要求 pinned 失效时“提示重新预览”。三条互相矛盾：pinned 过期/损坏后无法重新预览、无法重新 pin，restore 永远无法继续。
- 同时 `:541` 的 `RESTORE_DRAIN_TIMEOUT`、`:543` 的 `RESTORE_BACKUP_FAILED` 都要求“保留 marker、maintenance 保持 true”，但没有 cancel/abort 接口。结果是任何一次 pre-restore 备份失败或同步 drain 超时，所有写请求永久 503；重启后 marker 仍在（`:561`），仍然 503。文档没有“删除 marker / 取消恢复”的运维步骤。
- 要求修复：把备份 list/preview/export 加入 maintenance allowlist（它们只读，不写 workspace）；新增 `POST /api/workspace/backups/restore/cancel`（或 `DELETE restore-in-progress`）并定义其幂等语义、清 marker、清 maintenance、是否清 suspend；对 `RESTORE_BACKUP_FAILED`/`RESTORE_DRAIN_TIMEOUT` 明确“自动 abort 并清 maintenance”还是“保留 + 必须 cancel”。S10/S18 增加“失败后重新预览/取消后写入恢复”的用例。

### BK3 [高] 恢复等待只等 CalDAV，提醒调度仍可在 sent 重置后写回旧 sent

- 证据：§4.3 第 4 步只调用 `waitForInFlightSync(10_000)`；§2.7 明确该等待登记的是 `caldav-sync.ts` 的私有 `inFlight`（`:257-267`）。`notifications/scheduler.ts:188-222` 的 `runReminderCheck` 独立读取 state/workspace、发送推送，成功后写 `state.sent[key]=now` 并 `writeState`；它没有 maintenance/epoch 检查，也没有注册到 in-flight。
- 竞态：恢复第 5 步在锁内把 sent 重置为 `id|remind` 交集；若一个 reminder tick 在恢复前已读到旧 sent、在重置后才 `writeState`，会把已恢复条目的旧 sent 写回，导致恢复后提醒被误判为“已发送”而不再触发。S10 只测“sent 交集”，S18 只测 restore 阶段，均覆盖不到。
- 要求修复：把 reminder 调度纳入 `waitForInFlightSync`（或恢复时停止并等待 scheduler），并在 `writeState` 前检查 `isSyncMaintenance()`/epoch；明确 restore 期间 scheduler 是“暂停”还是“等待”。S10/S18 增加“reminder tick 跨恢复”的注入测试。

### BK4 [高] P2→P3 的 `writeWorkspace` 去导出与 `sync-control` 归属会造成构建/运行断裂

- 证据：§2.2 `:152` 要求 `writeWorkspace` 改为不导出，但调用方迁移表（`:154-160`）把 `routes/workspace.ts`、`caldav-sync.ts`、`routes/webdav.ts` 的迁移放在 P3；P2 只做 store（§9 `:733`）。P2 合入后这些文件仍 import `writeWorkspace`，TypeScript 构建直接失败，P2 无法单独通过 CI。
- 证据：`sync-control.ts` 的 `currentSyncEpoch/invalidateSyncEpoch/setSyncMaintenance/isSyncMaintenance/waitForInFlightSync` 定义在 §2.7 `:257-267`，被 P3 的 CalDAV/WebDAV epoch 检查（§2.2 迁移表）和 P1 的 `createApp` maintenanceGuard（§3.2 第 6 步 `:371`）引用；但 §9 没有任何 P 行在 P3 之前创建它，P7 才出现“marker/epoch/maintenance”（`:737`）。P3 无法编译 epoch 检查，P1 的 maintenanceGuard 也没有模块可 import。
- 要求修复：P2 保留 `writeWorkspace` 导出（标 `@internal`），P3 在迁移全部调用方的同一 PR 删除导出；在 P1 或 P2 先落地 `sync-control.ts` 的 no-op 骨架（epoch=0、maintenance=false、wait 立即 true），P7 再实现真实 epoch/maintenance/in-flight。或者把 P2+P3 合并为一个 PR。

### BK5 [中] S7 的 `%61pi` 断言按当前 createApp 顺序不会得到 401

- 证据：§3.2 第 4 步是 `app.use("/api", authMiddleware(token))`（`:370`），第 9 步 SPA 排除正则 `/^\/api(\/|$)/i`（`:378` 附近）。Express 4 的路由匹配使用未解码的 `req.url` 路径；用原生 Node HTTP 服务验证，curl 请求 `/%61pi/workspace/items` 时 `req.url` 仍是 `/%61pi/workspace/items`，`app.use("/api")` 不匹配，SPA 正则也不匹配，最终返回 `index.html` 200 而不是 401。S7 明确要求 `%61pi` → 401（§8.1）。
- 影响：S7 会失败；实现者若为了让 S7 过而把 auth 改成 `app.use(auth)` 全路径，会误伤 `/health` 和静态资源；若改成 `decodeURIComponent(req.path)` 又要定义非法编码（`%`、`%zz`）返回 400 还是 401。当前 SDS 没有这条契约。
- 要求修复：在 auth 之前增加“解码后大小写不敏感的 `/api` 前缀”守卫（非法编码返回 400），再挂 auth；明确 `/API`、`/Api`、`/api//`、`/%61pi` 的期望状态，并让 S7 同时断言“非 API 静态/SPA 仍 200”。这是契约级修复，不需要改路由实现。

## 非阻断问题

- **N1 删除最后一条 / 清空 workspace 被 `:148` 禁止。** `mutateWorkspace` 要求 tolerant parse 后“至少有一条可解析条目”，但正常删除最后一条、或用户手工清空 `## ` 块是合法状态；`readWorkspace` 对 ENOENT/空文件也返回空。应改为“文本无 `## ` 块时允许 0 条；有 `## ` 但 0 条可解析才拒绝”，并补 S2/S6 用例。
- **N2 WebDAV merge 丢 frontmatter/unknownBlocks。** `routes/webdav.ts:137-196` 只 `serializeWorkspace(items, notes)`，§2.5 的 `frontmatterRaw/unknownBlocks` 在 merge 路径没有合并规则；双方都有未知块时会静默丢失。需定义“保留本地文件级扩展；远端扩展追加/去重；冲突则 409 不写”。
- **N3 Calendar ICS 导出在 P5 后会 401。** `Calendar.tsx:39` 已经从 `api/workspace` 导入 `exportIcsDownloadUrl`（不是 SDS 说的 md-bridge），`:542` 用 `window.open`；`api/workspace.ts:249-258` 的 URL 不带 Authorization。§3.5 要求改 blob 仍然正确，但“当前走 md-bridge”是过期描述；P3 若只按“迁移旧导出”检查会误判已完成。P3/P5 必须把 `window.open` 改成 `exportIcs()` + blob，并让 F3 覆盖。
- **N4 S18 的崩溃矩阵没有可注入的 phase。** §4.3 第 2 步只写 `phase:"starting"`，之后不更新；S18 要求“写 marker 后/等待中/覆盖后状态重置前/清 marker 前”四个点，S10 要求“崩溃重启后 paused”。没有 phase 迁移或测试钩子，测试只能靠杀进程时序，不稳定。建议定义 `starting|draining|writing|resetting|done` 并提供一个测试专用 env（如 `RESTORE_CRASH_PHASE`）在对应点 `process.exit`。
- **N5 `getReminderStatus` 仍无 catch。** `notifications/scheduler.ts:264-299` 调 `readWorkspace()`，路由 `routes/notifications.ts:58-65` 捕获后 500；A5 要求后台读取失败不 500。状态接口可以返回 `{error}`/空统计，不应 500。
- **N6 Docker entrypoint 未按 §3.7 改。** `docker-entrypoint.sh:6-8` 无条件 `chown -R app:app /data`；只读挂载下失败被 `|| true` 吞掉，语义上不是“仅可写时 chown，失败 WARN 不退出”。P9 前改；不影响当前契约审阅。
- **N7 `WorkspaceHttpError` 的领域 code 未枚举。** §6 只给 400/404/409 大类；迁移 `routes/workspace.ts:298/398/446/651/813` 时，`ITEM_NOT_FOUND`、`LIST_NOT_FOUND`、`DUPLICATE_ID` 等具体 code 需要表，否则实现者会各自造字符串，前端无法稳定判断。
- **N8 CalDAV push 仍在响应无 ETag 时保留旧 etag。** `caldav-sync.ts:881-945` 的 `normalizeEtag(res.headers.get("etag")) ?? etag` 会保留旧值；§2.7 要求 `etag:null`。迁移时必须去掉旧值回退，否则下一轮永久 412。
- **N9 WebDAV merge 的 state 写失败被吞。** `writeSyncState` 失败只告警，workspace 已合并但 etag 仍旧，下一轮重复 merge；epoch 检查不能替代持久化。至少返回 warning/记录事件，并在 UI 显示“状态未保存”。
- **N10 sync conflicts 只存在内存 ring（D18 接受）。** 重启后未解决的冲突从 UI 消失，“查看冲突”可能显示 0，但本地/远端仍分歧；需在 UI/文档说明“仅本次会话”，或把冲突摘要落到 state（不新增历史文件）。
- **N11 `api/kanban.ts` 是死代码但不在 P3 删除清单。** 服务端 `routes/kanban.ts` 删除后该文件无调用方；P3 应一并删除，避免后续误用。`kanban-id.test.ts` 仍 import `routes/kanban`，必须改；`e2e-bridge.test.ts` 用的是 `md-ics-bridge`，P3 的“更新 e2e-bridge”并非必需。
- **N12 `ui-smoke` 的 axios mock 可能不兼容 `createApiClient`。** 现有 mock 只给 get/post/put/patch/delete；若 P6 的 client 用 `axios.create()` + interceptors，需要补 `create` 返回带 interceptors 的对象，否则 F1/F5 系列会因 mock 缺失而挂。
- **N13 `/api/workspace/info` 仍返回绝对 `filePath`。** v0.3.0 有 auth 可接受；v0.2.5 公开 LAN 会暴露路径。与 §2.1 “错误只给相对文件名”不冲突，但建议 info 同时给相对路径或明确 v0.2.5 可接受。
- **N14 `POST /api/sync/resume` 只清 suspend、由 UI 触发同步。** 若 UI 触发失败，suspend 已清但同步未发生；需定义幂等与失败提示，S? 补一条 resume 失败用例。

## 五行总结

1. v0.2 已把前两轮大多数安全/数据契约补全，B1/B3/B4/B5、A2/A3 可判关闭，B2/A1/A4/A5 仍为部分。
2. 仍有 5 个必须先修的阻断：P5/P6 与 P7/P8 坏中间版本、恢复失败无出口、reminder 跨恢复竞态、P2→P3 构建断裂 + sync-control 无归属、S7 `%61pi` 不成立。
3. 恢复设计是当前最大风险：maintenance 锁死 preview，pre-restore/drain 失败后无 cancel，S18 又缺少可注入 phase。
4. 备份/同步中心整体可实施，但 merge 的 frontmatter/unknownBlocks、CalDAV 旧 etag、state 写失败、conflicts 仅内存需要明确契约。
5. 建议按 BK1–BK5 修契约与 PR 边界后再进 P1；修完后可判“通过”，无需再改架构。
